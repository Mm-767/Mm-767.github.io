상태: 채택 · ADR-002(코인·구매는 RPC)에서 파생

## 문제

코인 잔액을 어떻게 저장하고, 미션 보상·아이템 구매에서 "돈만 나가고 아이템 안 옴" / "아이템만 오고 돈 안 나감" 반쪽 실패를 어떻게 막을까.

제약: 해커톤 규모(유저당 코인 이벤트 수십~수백 회) / 리포트가 구매 내역·총 획득 코인을 요구 / 조작된 클라이언트 방어 필요.

## 검토한 선택지

| 안 | 잔액 구하는 법 | 이력 | 잔액 정확성 | 비고 |
|---|---|---|---|---|
| A. coin_ledger 원장 | SUM(amount) | 있음 | 계산값이라 구조적으로 안 틀어짐 | 행 많아지면 SUM 느려짐 |
| B. profiles.coins 컬럼 | 컬럼 읽기 | 없음 | 동시 UPDATE로 틀어지면 복구 불가 | 구매 내역 불가 |
| C. 둘 다 (원장 + 캐시 잔액) | 컬럼 읽기 | 있음 | 두 곳 동기화 필요 | 대형 서비스 방식 |
| FIFO 캡 원장 | SUM(최근 50행) | 부분 | 오래된 행 삭제 = SUM이 그만큼 틀어짐 → 코인 증발 | 기각 |

## 결정

A. `coin_ledger` 추가 전용 원장, 잔액 = `SELECT SUM(amount) WHERE user_id=?`. 원장 행은 삭제하지 않는다.

미션 보상·아이템 구매·펫 슬롯 구매는 **Postgres RPC 함수**로 처리. 함수 안에서 `coin_ledger INSERT`(−가격) + `user_items/pets INSERT`(아이템)를 **한 트랜잭션**으로 묶는다 — 둘 다 커밋되거나 둘 다 롤백. "코인 충분한지" 확인도 함수 안에 있어 클라이언트가 건너뛸 수 없다.

`coin_ledger`에 `request_id uuid unique` 컬럼 추가 → 멱등키. 앱이 응답 유실로 같은 요청을 재시도해도 두 번째는 unique 위반으로 무시되어 딱 한 번만 처리된다.

## 근거

- 리포트가 이력을 요구하므로 원장은 어차피 필요. 원장이 있으면 잔액은 파생값으로 공짜.
- 해커톤 규모에서 `SUM(수십 행)`은 즉시 — B의 "빠름"이 무의미하고, A는 잔액이 틀어질 구조가 없다.
- 트랜잭션이 반쪽 실패를 원천 차단. RPC(DB 안 함수)여야 앱이 죽어도 그 틈이 없다.
- 멱등키가 네트워크 응답 유실 시 중복 처리를 막는다 (토스·스트라이프 방식).
- FIFO 삭제는 SUM 기반 잔액을 깨서 코인이 증발하는 버그 — 기각.

## 포기한 것

- 원장이 무한히 커진다 (해커톤 기간엔 수십 MB도 안 됨). 진짜 커지면 월별 스냅샷 행 + 아카이브로 C 전환 — 무해한 변경.
- 잔액 조회가 컬럼 읽기보다 살짝 무겁다 (해커톤 규모에선 체감 불가).

## 당시 몰랐던 것

- RPC 함수가 몇 개나 필요하고 얼마나 복잡해질지 미정 (미션 보상/구매/슬롯 각각인지 하나로 통합인지).
- reconciliation 배치(user_items ↔ coin_ledger 대조)는 오버킬로 판단 — 실제로 불필요한지 미검증.
- 멱등키를 클라이언트가 언제 새로 생성하고 언제 재사용하는지(재시도 정책) FE와 협의 안 됨.
- **이 ADR이 안 다룬 문제**: 멱등키는 같은 요청의 재시도만 막는다. 서로 다른 두 요청이 동시에 겹치는 경우는 [ADR-008](/posts/adr-008-코인-rpc-동시성-사용자-단위-advisory-lock)에서 따로 다뤘다.
