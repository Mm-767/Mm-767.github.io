상태: 채택

## 문제

마이그레이션을 손으로 `supabase db push`해서 반영했는데, 앞으로도 사람이 매번 기억해서 돌려야 하는 구조다. 또 테스트가 하나도 없어서 PR이 올라와도 자동으로 검증되는 게 없다. 멘토링에서 "민감한 키는 GitHub Actions로 돌려라"는 조언도 있었다. CI/CD를 도입하되 어디까지 할 것인가.

제약: 대회 마감까지 3주 미만, BE 1명, 배포 대상(AWS/Heroku/Render)은 아직 미정.

## 검토한 선택지

| 안 | 내용 | 지금 할 수 있나 |
|---|---|---|
| A. 마이그레이션 자동 push | supabase/migrations/ 변경 시 dev·main에서 db push | 가능 — 방금 손으로 한 절차를 그대로 자동화 |
| B. 테스트·lint 자동 실행 | PR마다 ruff + pytest | 가능 — 단, 테스트가 0개라 최소 1개를 같이 써야 함 |
| C. 앱 배포 자동화 | main push 시 FastAPI를 호스팅에 배포 | 불가 — 배포 대상이 아직 안 정해졌음 |

## 결정

**A + B만 도입한다. C는 보류.**

워크플로를 하나로 합치지 않고 둘로 나눠서, 트리거도 권한도 다르게 준다.

- `ci.yml` — pull_request 트리거. 가짜 env 값만 쓰고 시크릿 없음.
- `supabase-migrate.yml` — push 트리거 + `paths: supabase/migrations/**` 필터. 실제 시크릿 2개 사용.

## 근거

- CI와 CD는 실패의 의미가 다르다. CI 실패는 "merge하지 마라"고, CD 실패는 "실제 반영이 안 됐다"다. 하나로 묶으면 이 둘이 섞여서 어느 쪽이 깨졌는지 로그를 파야 알게 된다.
- 권한 분리가 더 중요하다. CI는 아무 PR에서나 돌아야 하는데, 그 워크플로에 실제 DB 시크릿을 주면 외부 기여자 PR이나 실수로 만든 브랜치에서도 그 토큰이 노출될 경로가 생긴다. 나눠두면 CI 쪽은 유출될 게 아예 없다.
- `paths` 필터가 있어야 주석 한 줄 고친 push가 실제 DB 접속을 유발하지 않는다.
- C는 배포 대상이 정해지지 않은 상태라 지금 만들면 버리게 될 가능성이 높다. ADR-002에서 FastAPI를 상시 배포하지 않기로 한 것과도 맞물린다.

## 구현 중 갈린 결정 — ruff 룰셋

워크플로를 써놓고 로컬에서 돌려보니 `ruff check .`가 기존 `app/main.py`에서 두 건을 잡았다(I001 import 정렬, BLE001 blind except). 이 환경의 ruff 기본 룰셋이 예상보다 훨씬 넓어서 생긴 일.

| 안 | 내용 | 비용 |
|---|---|---|
| A. 기존 코드를 고친다 | import 정렬 + except Exception 좁히기 | CI 도입이 명분인 남의 코드 수정으로 번짐 |
| B. 룰셋을 좁힌다 | select = E4/E7/E9/F | 나중에 더 엄격하게 가려면 다시 논의 필요 |

**B를 골랐다.** blind except는 FastAPI 핸들러 경계에서 예외를 400으로 바꾸는 정당한 패턴이지 버그가 아니다. 도구 의견에 맞추려고 남의 코드 스타일을 고치는 건 "CI 도입"의 범위를 넘는다. 진짜 에러(F)와 기본 스타일(E)만 잡는 선에서 시작한다.

같은 이유로 pytest가 `app` 패키지를 못 찾는 문제도 코드 구조를 바꾸는 대신 `pyproject.toml`에 `pythonpath = ["."]` 한 줄로 해결했다.

## 포기한 것

- 엄격한 lint. 지금 룰셋은 import 정렬·네이밍 같은 건 안 잡는다. 팀이 커지거나 코드가 늘면 다시 올려야 한다.
- 배포 자동화. 대회 마지막 주에 손으로 배포하거나, 그때 가서 다시 만들어야 한다.
- 테스트 커버리지. `/health` 하나만 있어서 "앱이 뜼는가" 외에는 아무것도 보장하지 않는다. 초록불을 과신하면 안 된다 (→ 이 문제가 [ADR-009](/posts/adr-009-ci에서-db테스트-실행-supabase-start-통째로)로 이어진다).

## 당시 몰랐던 것

- `supabase-migrate.yml`이 실제로 동작하는지 아직 검증되지 않았다. 확인만을 위해 의미 없는 마이그레이션을 실제 DB 히스토리에 영구히 남기는 게 싫어서, 다음 진짜 스키마 변경 때 검증되도록 미뤄두었다. 그때 실패하면 그 PR에서 고쳐야 한다.
- CI 러너가 매번 `pip install`을 처음부터 하는 구조라(캐시 없음) 나중에 의존성이 늘면 느려질 수 있다. 지금은 22초라 상관없다.
- `requirements.txt`에 버전 고정이 없어서, 어느 날 의존성 새 버전이 나오면 CI가 갑자기 깨질 수 있다.

## 결과

PR #2에서 CI 워크플로 실제 실행 — 22초, 성공(ruff + pytest 통과). 마이그레이션 워크플로는 아직 측정 안 됨.
