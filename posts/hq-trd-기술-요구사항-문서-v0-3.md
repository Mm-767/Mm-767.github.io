## 0\. v0.2에서 무엇이 바뀌었나

| # | v0.2 | v0.3 | 파급 |
| --- | --- | --- | --- |
| 1 | 클라이언트 = PWA 확정 | **Flutter 하이브리드** | 3장 전체 재작성 |
| 2 | 백그라운드 지오펜싱 = 불가, 설계 제외 | **네이티브 지오펜싱 도입** | 3.2 |
| 3 | 위치 권한 = 있으면 좋고 | **3단계 선택 + 단계별 기능 차등** | 3.3 |
| 4 | 배포 = 정적 호스팅 URL | **APK 직배포 / iOS Xcode 설치** | 8장 |
| 5 | 캘린더 = 온디바이스 검토 | Google Calendar OAuth 확정 | 5.5 |

전환 근거는 **앱스토어 배포를 포기했기 때문**이다.

> "앱스토어에 안 올리고 진짜 시험만 한다는 가정이면, 해커톤 레벨에서 그런 것까지 세세하게 보진 않을 것 같아서."

PWA를 고른 유일한 이유가 배포 편의였는데, 심사를 안 받기로 한 순간 그 이점이 사라진다. 반대로 하이브리드는 지오펜싱·FCM·로컬 DB를 전부 열어준다. **교환 조건이 명확하게 유리해졌다.**

## 2\. 시스템 아키텍처

### 2.1 구성

```
      [ Flutter 하이브리드 앱 ]
       Android APK / iOS Xcode 설치
              │  HTTPS / JWT
              ▼
   ┌──────────────────────┐        ┌──────────────────────┐
   │  Spring Boot (Main)  │◄─REST─►│   FastAPI (AI/ML)    │
   │  인증 · CRUD · 트랜잭션  │        │ 루틴생성 · 추천 · 챗봇  │
   └──────────┬───────────┘        └──────────┬───────────┘
     Flyway 소유 (읽기+쓰기)          hq_ai 롤 (SELECT + adjustments INSERT)
              ▼                                ▼
           ┌────────────────────────────────────┐
           │          PostgreSQL                │
           └────────────────────────────────────┘

  외부: OpenAI · 카카오맵 · Google Calendar · FCM
  로컬: SQLite (범위 미결 — 4.4)
```

### 2.2 컴포넌트 책임

| 컴포넌트 | 책임 | 하지 않는 것 |
| --- | --- | --- |
| Flutter 앱 | 화면, **지오펜스 등록·수신**, 권한 관리, FCM 수신, 로컬 캐시 | 판정 로직, 난이도 계산 |
| Spring Boot | OAuth·JWT, 도메인 CRUD, 트랜잭션, Flyway 마이그레이션 | AI 추론, `routine_tasks.action_id` 직접 UPDATE |
| FastAPI | 루틴 초안, 추천, 판정 근거, 챗봇 | 스키마 변경, `adjustments` 외 쓰기 |
| PostgreSQL | 저장 + 무결성 + **트리거 3종** | 인가(RLS 미사용) |

### 2.3 서비스 경계

`hq_ai` 롤에 `GRANT SELECT` 전체 + `adjustments` INSERT만 부여한다. 추천 서비스가 `task_logs`를 오염시키는 사고를 **애플리케이션 코드가 아니라 DB 권한으로** 막는다.

난이도 조정의 유일한 입구도 `adjustments` INSERT다. `trg_apply_adjustment`가 실제 적용을 수행하므로 Spring이 `routine_tasks.action_id`를 직접 쓰면 이중 적용이 된다.

### 2.4 클라이언트 — **\[확정·변경\]**

**Flutter 하이브리드.** 스토어 배포를 하지 않는 전제이며, 그 대가로 다음을 얻는다.

|  | PWA (v0.2) | Flutter 하이브리드 (v0.3) |
| --- | --- | --- |
| 백그라운드 지오펜싱 | 불가 | **가능** |
| FCM 푸시 | iOS는 홈화면 추가 필요 | 정상 |
| 로컬 DB | 제한적 | **SQLite 가능** |
| 걸음 수·센서 | 불가 | 가능 (Phase 2) |
| 배포 | URL 하나 | **APK / Xcode 설치** (8장) |

Flutter를 고른 이유는 멀티 플랫폼이라 나중에 웹으로도 뺄 수 있다는 것이다 — 8/6 회의에서 "선택지는 열려 있다"고 정리한 부분이다.

## 3\. 위치 기반 — **\[전면 재작성\]**

### 3.1 8/6 회의에서 막혔던 지점

PWA는 백그라운드 위치를 받을 수 없어 이동 트래킹과 장소 진입 감지가 불가능했고, 우회안(화면 켜두기)은 배터리 때문에 기각됐다. **하이브리드 전환이 이 문제를 통째로 해소한다.**

### 3.2 지오펜싱 — 폴링이 아니다

8/6 심야에 팀이 직접 확인한 내용이 정확하다.

> "계속 추적하는 게 아니고, 저전력으로 감시하다가 경계에 들어오거나 나갈 때 이벤트 기반으로 앱을 깨우는 방식."

| 플랫폼 | API |
| --- | --- |
| Android | `GeofencingClient` (Google Play Services) |
| iOS | `CLLocationManager` region monitoring |

앱이 좌표를 주기적으로 조회하지 않는다. **OS가 저전력 경로로 감시하다가 경계 교차 시에만 앱을 깨운다.** "계속 API를 쏘면 부담 아니냐"는 우려는 이 방식에는 해당하지 않는다.

```
[등록]  사용자가 장소 지정 (카카오맵 검색)
          → places INSERT
          → routines.place_id 연결 (schedule_type='place')
          → 앱이 OS에 지오펜스 등록

[감지]  OS가 진입 감지 → 앱 콜백 기동
          → POST /places/{id}/enter   (좌표 아님, 장소 id만)
          → 서버가 place_visits 기록 + 해당 루틴 반환
          → 로컬 알림 / FCM
```

**좌표는 서버로 보내지 않는다.** 클라이언트가 보내는 것은 "몇 번 장소에 들어왔다"는 사실뿐이다. 서버에 공간 연산이 필요 없어 PostGIS 미채택 판단이 유지된다.

| 제약 | 값 | 대응 |
| --- | --- | --- |
| 지오펜스 등록 상한 | Android 100 / **iOS 20** | 활성 장소만 등록 |
| 감지 지연 | 수십 초~수 분 | 즉시성 요구 UX 금지 |
| 재부팅 시 소실 | 등록 해제됨 | 부팅 완료 수신 후 재등록 |
| 반경 하한 | GPS 오차 | `radius_m` 기본 300, 최소 100 (스키마 제약) |

### 3.3 위치 권한 3단계 — **\[확정\]**

8/6 심야에 결정된 방식이다.

> "개발할 때는 다 구현을 해놓고, 사용자가 선택한 옵션에 따라 제한시켜 놓는 거죠."

| 사용자 선택 | 동작 | 영향 |
| --- | --- | --- |
| **항상 허용** | 지오펜싱 전체 | 앱이 꺼져 있어도 진입 알림 |
| **앱 사용 중만** | 앱 진입 시 1회 위치 조회 후 매칭 | 자동 알림 없음 |
| **거부** | 위치 기능 전체 비활성 | `schedule_type='time'` 루틴만 |

온보딩에서 모달로 선택을 받고, 각 단계의 차이를 문장으로 설명한다. **구현은 전부 해두고 런타임에 잠그는 방식**이라 분기 비용이 낮다.

**\[확정\]** 8/6 회의 결정에 따라 **권한 요청 화면을 와이어프레임과 유저 플로우에 추가**한다. iOS는 한 번 거부하면 앱 내에서 다시 물을 수 없으므로, **설정 앱으로 보내는 화면**이 별도로 필요하다.

> **거부해도 앱이 죽지 않아야 한다.** 시간 기반 루틴이 완전히 동작하는 것이 폴백이다. 위치는 증강이지 전제가 아니다.

## 4\. 데이터 설계

`hq-schema-v0.6.sql`이 정본이다. 여기서는 TRD 관점의 근거만 남긴다.

### 4.1 구조 — 8 테이블 + 뷰 1개 + 트리거 3개

| 층 | 테이블 |
| --- | --- |
| 사용자·동의 | `users` `user_consents` |
| 장소 | `places` `place_visits` |
| 정의 | `actions` `routines` `routine_tasks` |
| 실행 | `routine_runs` `task_logs` |
| 조정 | `adjustments` |
| 연동 | `fcm_tokens` `calendar_connections` |
| 판정 | `v_daily_states` (뷰) |

### 4.2 설계 근거 다섯 가지

**난이도는 컬럼이 아니라 좌표다.** `actions`가 `(ladder_key, difficulty)`로 유니크하고, 조정은 같은 `ladder_key` 안에서만 움직인다. `trg_apply_adjustment`가 사다리 교차를 거부한다.

**과거 기록은 동결된다.** `task_logs.action_id`가 그날의 난이도 스냅샷이다. `trg_task_logs_snapshot`이 삽입 시 자동으로 채우고 `trg_task_logs_freeze`가 이후 변경을 거부한다. 난이도를 낮춰도 과거 기록의 의미가 소급 변하지 않는다.

`routine_runs`**는 지연 생성한다.** 스케줄러 배치가 아니라 `GET /today` 첫 호출 때 만든다. **배치가 안 돌아서 오늘 화면이 비는 실패 모드를 아예 없애기 위해서다.** 시연 환경에서 크론이 죽어 있어도 화면이 나온다.

**판정은 저장하지 않는다.** `v_daily_states`가 뷰라서 컷오프(현재 0.7/0.3)를 고치면 과거까지 즉시 재판정된다. 컷오프가 미결이므로 이 형태가 맞다.

**조정에 낙관적 잠금이 걸려 있다.** `before_action_id`가 현재 값과 다르면 `stale adjustment`로 실패한다. AI와 사용자가 동시에 난이도를 건드려도 덮어쓰기가 안 난다.

### 4.3 인가는 애플리케이션 책임

RLS를 쓰지 않으므로 `user_id` 조건이 빠진 쿼리 하나가 전체 노출로 이어진다. 리포지토리 조회 메서드에 `userId`를 필수 파라미터로 두고, **통합 테스트에 타인 데이터 조회 시도 케이스를 반드시 포함한다.**

`places`가 집·직장 좌표를 담으므로 이 원칙의 중요도가 올라갔다.

### 4.4 로컬 SQLite — **\[미결\]**

8/6 심야에 "SQLite가 누락된 거 아니냐"는 지적이 있었고 정리되지 않았다.

**서버 스키마와 한 장으로 합칠 수 없다.** 목적이 다르다. 먼저 **로컬에 둘 데이터의 범위**부터 정해야 스키마가 나온다. 후보는 셋이다.

| 후보 | 로컬에 둘 이유 | 판단 |
| --- | --- | --- |
| 오늘의 루틴 캐시 | 오프라인·비행기 모드에서도 체크 가능 | \[검토\] 값이 큼 |
| 지오펜스 등록 목록 | OS 재등록 시 서버 왕복 불필요 | \[검토\] 값이 큼 |
| 위치 원시 로그 | "민감한 데이터는 로컬에" | **\[미결\]** 수집 자체를 안 하기로 했으므로 불필요할 수 있음 |

**\[검토\] 앞의 둘만 로컬에 두고, 원시 위치는 아예 저장하지 않는다.** 그러면 SQLite는 캐시일 뿐이라 별도 ERD가 필요 없고 테이블 2개로 끝난다. 오늘 회의에서 확정할 것.

## 5\. API 설계 — \[검토\]

### 5.1 인증

`POST /auth/{provider}` — 클라이언트가 kakao/google 인가 코드를 받아 교환, Spring이 자체 JWT 발급. JWT `sub` = `users.id`.

**\[미결\]** 비로그인(게스트) 지원 여부는 8/6 회의 미결 2번이다. 시나리오 문서에 로그인 자체가 빠져 있어 먼저 정해야 한다.

> **\[검토\]** 게스트를 지원한다면 **완전 로컬**을 권한다 — 서버에 익명 계정을 만들면 이관·정리 로직이 전부 따라온다. 로컬 전용이면 백엔드 작업량이 0이다.

### 5.2 주요 엔드포인트

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| `POST` | `/auth/{provider}` | 소셜 로그인 |
| `POST` | `/consents` | 동의 기록 (append-only) |
| `GET` `POST` | `/places` | 장소 목록·등록 |
| `POST` | `/places/{id}/enter` | **지오펜스 진입** (좌표 미포함) |
| `POST` | `/places/{id}/exit` | 이탈 (`place_visits.exited_at`) |
| `GET` | `/today` | 오늘 루틴 + 신호. `routine_runs` **지연 생성 지점** |
| `POST` | `/logs` | 수행 기록 |
| `GET` | `/states?from=&to=` | 기간별 판정 (`v_daily_states`) |
| `GET` | `/adjustments` | 난이도 변경 이력 + `reason` |
| `POST` | `/devices/fcm` | FCM 토큰 등록 |
| `POST` | `/chat` | 챗봇 |

`POST /logs`는 `routine_run_id`, `routine_task_id`, `status`만 받는다. `action_id`는 트리거가 채우므로 클라이언트가 보내지 않는다.

### 5.3 서버 간 통신

| 경로 | 용도 |
| --- | --- |
| `POST /ai/routines/draft` | 루틴 초안 |
| `POST /ai/recommendations` | 추천 행동 |
| `POST /ai/signal/evaluate` | 판정 + 조정 제안 |
| `POST /ai/chat` | 챗봇 |

프로토콜은 REST. 팀 규모 대비 gRPC의 이득이 크지 않다.

### 5.4 외부 연동

| 대상 | 용도 |
| --- | --- |
| OpenAI API | 루틴 생성·챗봇 (Structured Outputs) |
| 카카오맵 | 장소 검색 |
| Google Calendar | 일정 읽기 (5.5) |
| FCM | 푸시 |

### 5.5 캘린더

`calendar_connections`에 `refresh_token_enc`(암호화)와 `scope`를 저장한다. 스코프는 `calendar.readonly`.

**추출 범위는 빈 시간대와 장소 문자열까지.** 일정 제목·본문은 저장하지 않는다.

**\[검토\]** `calendar.readonly`는 구글 민감 스코프라 프로덕션 배포에 검증이 필요하다. 테스트 사용자 등록(100명 상한)으로 충분하지만, **심사위원 계정을 미리 등록해두지 않으면 시연 당일 로그인이 막힌다.**

## 6\. AI 파이프라인

### 6.1 원칙

생성형보다 **기존 데이터 기반 추천 우선.** LLM은 `actions` 라이브러리에서 고르고 이유를 설명하는 역할이다. Structured Outputs로 스키마를 강제해 존재하지 않는 action 생성을 차단한다.

### 6.2 루틴 설계

```
온보딩 + 목표 + 캘린더 빈 시간대·장소
  → actions 후보 필터 (category, difficulty 하한)
  → LLM이 조합·배치 (Structured Outputs)
  → routines / routine_tasks 초안 → 사용자 확인 → Spring 저장
```

### 6.3 이상치 패턴 감지

`v_daily_states`가 `completion_rate`를 계산하고 green/yellow/red를 판정한다. **\[미결\]** 컷오프 0.7/0.3은 확정 전이다 — 뷰만 고치면 되므로 늦게 정해도 된다.

`gray`는 이미 뷰에 있다. **수행할 태스크 자체가 없는 날**을 뜻하며, 8/6 회의의 "미접속·데이터 공백 날 처리"(미결 4번)와는 다른 개념이다. 혼동하지 말 것.

> **\[미결·중요\]** 미접속 날을 실패로 볼지 비워둘지는 아직 미정이다. 8/6 회의에서 **"비워두고 회복 루틴으로 처리"** 방향이 나왔다. 확정되면 `v_daily_states`가 아니라 그 위의 표시 레이어에서 처리한다 — 뷰는 있는 그대로를 계산하고, "쉬는 날"의 해석은 애플리케이션 몫이다.

### 6.4 점진적 복귀

```
red 신호 또는 연속 성공
  → 같은 ladder_key 내 인접 difficulty 선정
  → 사용자 노출 문구(reason) 생성
  → adjustments INSERT → 트리거가 적용
```

`reason`은 로그가 아니라 **사용자에게 보여줄 문장**이다.

### 6.5 챗봇

루틴 설명 + 자연어 수정. **LLM 출력이 DB에 직접 반영되지 않는다.**

```
발화 → 컨텍스트 조립 → LLM (Structured Outputs)
   ├ 설명형 → 텍스트만
   └ 수정형 → { intent, target_task_id, proposed_action_id, reason }
               → 사용자 확인 → Spring이 저장
```

### 6.6 AI가 DB를 읽는 방식 — **\[검토\]**

**마크다운/JSON 직렬화. FAISS는 도입하지 않는다.**

`actions`는 수십 행, 사용자 루틴은 수~수십 행이라 통째로 프롬프트에 넣어도 컨텍스트가 남는다. 벡터 검색은 후보가 너무 많아 다 못 넣을 때 쓰는 도구다. 필요해지면 pgvector로 PostgreSQL 안에서 해결하면 인프라가 늘지 않는다.

### 7.2 보안

| 항목 | 수단 |
| --- | --- |
| 인가 | 모든 조회에 `userId` 강제 (4.3) |

| 캘린더 토큰 | 앱에서 암호화 후 `bytea` 저장 |
| 프롬프트 인젝션 | 아래 |

**프롬프트 인젝션** — 완화 수단 중 공짜인 둘은 그냥 넣는다. ① 챗봇에 쓰기 권한을 주지 않는다 ② `proposed_action_id`가 실제 존재하고 해당 사용자 소유인지 서버가 검증한다. 둘 다 정상 동작에도 필요한 검증이라 추가 비용이 없다.

### 7.3 개인정보

| 데이터 | 등급 | 처리 |
| --- | --- | --- |
| 지정 장소 좌표 | **높음** | 사용자 직접 등록 |
| 실시간 위치 | 높음 | **서버 전송 없음** (3.2) |
| 방문 이력 | 중간 | 장소 id + 시각 |
| 캘린더 | 높음 | 빈 시간대·장소만, 제목 미저장 |
| 건강·피부 | **검토 필요** | 범위 밖 |

`user_consents`가 append-only라 철회도 새 행으로 남는다. `location`·`calendar`·`health_data` 스코프가 이미 분리돼 있다.

**\[미결·중요\]** 8/6 회의 미결 1번 — **연령 기준.** 문서는 "18세 이상 성인"인데 페르소나에 10대가 있다. 만 14세 미만이 포함되면 법정대리인 동의 절차가 필요해지고 가입 플로우가 통째로 바뀐다. **위치까지 수집하므로 이건 화면 하나가 아니라 구조 문제다. 오늘 반드시 닫아야 한다.**

### 7.4 데이터 무결성

하드 삭제 금지, `archived_at` 소프트 삭제. `user_consents`는 트리거로 UPDATE·DELETE 자체가 막혀 있다.

**알려진 한계** — `v_daily_states`의 분모는 현재 살아있는 `routine_tasks` 수다. 과거에 태스크를 추가·삭제하면 그날의 완료율이 소급 변동한다. 정확히 하려면 run 생성 시점의 태스크 수를 `routine_runs`에 박아야 하는데, 현재 스코프에서는 과설계로 판단했다. **시연 중 과거 데이터를 건드리지 않으면 드러나지 않는다.**

## 10\. 리스크와 미결

### 10.1 기술 리스크

**테스트 기기 편중** (8.2). 가장 실질적인 리스크다. 안드로이드 실기기 1대 확보를 권한다.

**서브 기능 4개가 각각 다른 파이프라인.** 멘탈 코치·장소 피드백은 재사용, 식단·캐릭터는 신규 구축이다. Phase 2에서 별개 프로젝트로 취급한다.

**OpenAI 의존.** 루틴 생성 실패 시 규칙 기반 폴백을 두면 시연 중 API 장애에도 화면이 비지 않는다.

### 10.4 용어

기능 ④의 정식 명칭은 \*\*"이상치 패턴 감지"\*\*다. "이탈 신호 감지"와 혼용되고 있으니 통일할 것.
