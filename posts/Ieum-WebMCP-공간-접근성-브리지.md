**시각장애인이 기차 좌석을 '직접' 고르게 만드는 WebMCP 구현.**

요약해서 들려주는 대신 공간 구조 자체를 도구로 노출해, 질의·비교·경로는 에이전트가 하고 **판단은 사용자가** 하게 한다.

|---|---|
| 기간 | 2026-08-30 ~ 09-03 (5일) |
| 대회 | The WebMCP Challenge — OpenAI 주최, Devpost 운영. 참가 7,078명, 상금 $35,000, 상위 10팀 수상 |
| 저장소 | [Web-MCP-MJU/Ieum](https://github.com/Web-MCP-MJU/Ieum) |
| 내 몫 | 도메인·앱·어댑터 계층 + 테스트 94개 (해당 파일 blame 100%) |
| 팀원 몫 | 데모 홈페이지 |

## 왜 만들었나

사회에 도움이 되는 걸 만들어보고 싶었다. AI가 이 방향으로도 쓰이면 좋겠다는 생각이었고 동기는 그게 전부다.

### 심사 기준을 보고 맞춰 설계했다

심사위원은 Chrome·Shopify·Cloudflare·Vercel·Netlify·OpenAI 엔지니어들. 기준 4개가 공개돼 있었다.

| 심사 기준 | 대응 |
|---|---|
| WebMCP Leverage — 사소하지 않은 실제 구현인가 | 도구 9개, 도메인 1,500줄, 테스트 94개 |
| Execution — PoC가 아니라 완결된 경험인가 | 검색 → 비교 → 경로 → 확정까지 한 흐름 |
| Potential Impact — 실제 문제를 납득시키는가 | **미국 법령으로 근거를 댔다** — 아래 참조 |
| Creativity — 기존과 다른가 | 요약을 주는 대신 구조를 노출 |

**미국 법령을 고른 건 의도적이다.** 심사가 미국에서 이뤄지니 한국 기준으로 썼으면 심사자가 검증할 수 없는 근거가 된다. Potential Impact는 "납득시키는가"를 보는 항목이고, 납득의 기준은 읽는 사람 쪽에 있다.

---

## 문제

스크린리더는 좌석표를 **요약해서** 읽어준다. 그런데 좌석은 **위치 자체가 정보**다. "화장실에서 몇 걸음", "통로 쪽인지"를 확인할 수 없으면 사용자는 남이 골라준 걸 받아들이게 된다.

WCAG 2.2는 표의 **의미적** 연결만 요구하고 공간 관계는 요구하지 않는다. 표준을 다 지켜도 이 문제가 남는다. 법령은 "충분한 상세"를 요구하지만 그걸 담을 표준 스키마가 없어 전부 자유 텍스트다.

## 검토한 선택지

| 안 | 내용 | 한계 |
|---|---|---|
| A. ARIA 속성 보강 | 표준 안에서 해결 | 읽히는 건 여전히 선형 텍스트. 60석 비교하려면 60번 들어야 함 |
| B. 요약 API + 음성 안내 | 구현이 쉬움 | "대신 요약해준다"는 구조가 그대로. 사용자가 검증 불가 |
| **C. WebMCP 도구로 구조 노출** | 질의·비교·경로는 에이전트, 판단은 사용자 | 아직 표준이 아님 — 아래 별도 절 |

**근거.** 앞의 둘은 정보량을 줄여서 접근성을 만드는데, 문제의 본질은 정보량이 아니라 **되물을 수 있느냐**라고 봤다. "그럼 3열 통로석은?"이 가능해야 독립적인 판단이다.

---

## 도구를 어떻게 쪼갰나

**어떻게 쪼개느냐에 "판단은 사용자가"가 걸려 있다.**

- `query`(조건 검색)와 `compare`(2~4석 동일 축 비교)를 일부러 분리. 합치면 "최적 좌석"을 돌려주는 요약 구조로 되돌아간다
- `select`와 `confirm` 분리. 같은 도구면 120초 대기가 의미가 없다

```
"화장실 가까운 창가석 있어?"
  → a11y.query      후보 3개
  → a11y.compare    같은 축에서 나란히 (걸음 수·통로 접근·가격)
  → 사용자가 고름
  → a11y.get_route  실제 걸어가는 길
  → a11y.confirm    사람이 승인 (120초)
```

중간에 "그럼 3열은?"이 언제든 끼어들 수 있다. 이게 요약을 받는 것과의 차이다.

```
src/domain/   1,485줄   순수 계산 — WebMCP도 DOM도 모름
src/app/        567줄   유스케이스 9개 + 선택 상태
src/webmcp/     319줄   어댑터  ← 표준에 묶인 유일한 곳
tests/           94개   경로 26 · 질의 27 · 앱 27 · WebMCP 9 · 계약 5
```

**의존 방향이 한쪽이다.** `webmcp/`가 `app`·`domain`을 참조하지 반대는 없다. 검사로 확인 — `domain`·`app`에 `webmcp` import 0건, `domain`에 DOM API 0건.

## 배운 것 다섯

### 1. 돌아선 뒤의 걸음을 돌기 전 기준으로 말하지 않는다

안내가 `Turn around, toward the rear of the car. Walk 58 ft behind you...`로 나왔다. 회전을 따른 사람은 이미 뒤를 보고 있으므로 그 걸음은 behind가 아니다. 눈으로 보는 사람은 넘어가지만 듣는 사람에겐 그대로 틀린 길이다. 표기 방식 3가지(자기중심·차량축·시계)에서 모두 회귀를 잠갔다.

### 2. 렌더링된 값을 소스 데이터로 쓰지 않는다

세그먼트에 `direction: "left"`를 저장했더니 실제 각도를 버리게 돼 시계 표기에서 "10시 30분"을 만들 수 없었다. `bearing`에 각도를 담고 좌우·회전·총계는 렌더에서 파생시켰다.

같이 고친 것 — `Σround(x) ≠ round(Σx)`라 구간을 세며 따라오던 사람에게 안내문이 스스로 모순됐다. 총계를 표시값의 합으로 바꿈.

### 3. 한 번에 다 말하지 않는다

눈으로 보는 사람은 화면을 다시 보면 되지만 듣는 사람은 되돌아갈 수 없다. 4구간을 넘으면 도달 가능한 랜드마크에서 끊고 체크포인트를 낸다. 이어지는 호출은 이미 지나온 문을 되돌아가지 않도록 남은 관문만 계획한다. UX 판단이 데이터 구조로 내려온 자리.

### 4. 계약이 환경에 따라 달라지면 계약이 아니다

확정 대기 타이머에 `unref`를 걸어뒀다. 그런데 `unref`된 타이머는 이벤트 루프를 살려두는 다른 일이 있을 때만 울린다. 즉 아무도 기다리지 않으면 120초 타임아웃이 아예 발생하지 않는다.

`node:test`가 루프를 살려두어 기존 테스트로는 통과했다. 별도 프로세스에서 확정 하나만 두고 기다리는 회귀 테스트를 넣고, `unref`를 되돌리면 실패하는 것까지 확인했다.

### 5. 어림값이면 어림값이라고 말한다

거리 축이 "about 12 steps"를 만드는데 비교 결과에 캐비엇이 빠져 있었다. 걸음 수는 보폭에 따라 달라져 어림임을 함께 말하지 않으면 정확한 수치로 오해한다. 스키마 optional 필드라 계약 테스트로는 안 잡히는 자리였다.

## 표준이 아닌 것 위에 지었다

> **WebMCP는 아직 표준이 아니다.** W3C Web Machine Learning 커뮤니티 그룹의 제안 단계고, Chrome은 `chrome://flags/#enable-webmcp-testing`으로 플래그를 켜야 동작한다. 기본 지원되는 곳은 ChatGPT 인앱 브라우저 정도. 대회 자체가 "emerging open standard를 함께 만들어보자"는 취지였다.

그럼 표준이 안 되면 헛수고인가. 설계 단계에서 먼저 던진 질문이다.

답은 계층 분리다. 표준에 묶인 건 어댑터 319줄, 전체의 13%뿐이다. 공간 구조를 질의 가능한 데이터로 모델링한 것, 방위각을 저장하고 표현을 파생시킨 것, 체크포인트로 끊는 것, 어림값에 캐비엇을 다는 것 — 전부 전송 방식과 무관한 판단이다. REST든 함수 호출이든 다른 에이전트 프로토콜이든 어댑터만 갈아 끼우면 된다.

계층 분리를 "좋은 설계라서" 한 게 아니라 **기반 기술이 불확실해서** 했다고 말할 수 있으면, 그건 원칙이 아니라 구체적인 리스크 대응이 된다.

접근성 문제는 WebMCP가 표준이 될 때까지 기다려주지 않는다. 표준이 아니어서 못 하는 게 아니라, 표준이 없어서 지금 아무도 안 하고 있는 쪽을 골랐다.

## 참고자료 — 실제 사례

Usablenet 블로그의 마이클 테일러(Michael Taylor) 연재 — 본인이 시각장애인인 웹 접근성 전문가가 항공사 사이트를 직접 써보며 기록한 시리즈. 문제 정의의 1차 근거로 사용했다.

핵심 증언과 진단은 이렇다.

- 좌석을 골랐다고 생각했는데 아무것도 저장되지 않았고, 결국 의도한 적 없는 중간 좌석으로 탑승했다
- 좌석도가 이미지나 PDF여서 무의미한 문자로 읽힌다
- 표 형태여도 행·열 라벨만 있고 맥락과 가용 여부 단서가 없다
- 좌석도는 **동적이라 대체 텍스트로 대응할 수 없다** ← 선택지 A를 버린 근거

마지막 항목이 중요하다. "동적이라 alt 텍스트로 안 된다"는 진단이, ARIA 보강(안 A)을 버리고 구조 노출(안 C)로 간 선택을 외부 근거로 받친다.

## 어디까지 갔고 무엇이 없나

실제 에이전트 런타임에 붙여 도구 호출이 되는 것까지 확인했다. 다만 데모 페이지이고 운영 배포가 아니다.

> **실제 시각장애인 사용자에게 검증하지 못했다.** 5일이라 법령과 표준 문서를 근거로 설계했고, 지표는 도구가 규격대로 동작하는지까지다. 이 방향이 실제로 도움이 되는지는 사용자에게 물어봐야 알 수 있다. 이 프로젝트에서 제일 크게 빈 자리다.
