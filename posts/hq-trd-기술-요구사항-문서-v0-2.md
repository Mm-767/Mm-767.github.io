## 0\. v0.1에서 무엇이 바뀌었나

8/5 회의로 이 문서의 전제 두 개가 바뀌었고, 하나가 확정되었다.

| # | v0.1 | v0.2 | 파급 |
| --- | --- | --- | --- |
| 1 | 위치 기반 = 서브 기능 후보, 범위 밖 | **위치 기반 = 메인 기능** | 3장 신설 |
| 2 | AI 챗봇 = 위상 미결, 범위 밖 | **챗봇 = 핵심**, 멘탈 코치를 흡수 | 6.5 신설, 7.2에 신규 공격면 |
| 3 | 클라이언트 = Flutter vs PWA 미결·최우선 | **PWA 확정** | 3장의 구현 방식이 여기 종속 |

②이상치 패턴 감지와 ③점진적 복귀는 이번 회의에서 부정되지 않았다. v0.1의 4·6장이 그대로 유효하다.

## 1\. 개요와 범위

### 1.1 목적

v0.1과 동일하다. 무엇을 만들지는 PRD, 만족 조건은 SRS, **구현 수단**만 이 문서가 다룬다.

### 1.2 대상 기능 — **\[변경\]**

**메인 (Phase 1 — 8/7 개발 시작 대상)**

| 기능 | 상태 | 이 문서에서 다루는 범위 |
| --- | --- | --- |
| ① AI 루틴 설계 | \[확정\] | 2·5·6장 |
| ② 위치 기반 루틴 배치·전환 | **\[확정·신규\]** | 3장 |
| ③ 일정/캘린더 연동 | \[확정\] | 5.5 |
| ④ 이상치 패턴 감지 (Green/Yellow/Red) | \[확정\] | v0.1 6.3 유효 |
| ⑤ 점진적 루틴 복귀 | \[확정\] | v0.1 6.4 유효 |
| ⑥ AI 챗봇 (루틴 설명 + 자연어 수정) | **\[확정·승격\]** | 6.5 |

**서브 (Phase 2 — 구현 못 하면 드롭)**

| 순위 | 기능 | 기술 재사용 | 신규 비용 |
| --- | --- | --- | --- |
| 1 | AI 멘탈 코치 | 챗봇 그대로 (프롬프트 + 트리거 조건만 추가) | 거의 없음 |
| 2 | 장소 피드백 | ②의 방문 로그 재사용 | 낮음 |
| 3 | 식단 기록 | — | **VLM 파이프라인 신규** |
| 4 | 캐릭터 | — | 디자인 에셋 + 상태 관리 신규 |

앞의 둘은 이미 만드는 것에 얹는 것이고, 뒤의 둘은 새로 파는 것이다. 회의에서 정해진 우선순위와 기술 비용 순서가 일치한다.

> **PRD 작성 시 주의** — 서브 4개를 메인과 같은 층에 나열하면 코드 생성 도구가 4개를 모두 스캐폴딩한다. "구현 못 하면 드롭"은 사람의 의도이지 도구의 동작이 아니다. 문서상 **Phase 2로 물리적으로 분리**할 것.

### 1.3 범위 밖

*   피부 스캔 (회의에서 "욕심 기능"으로 언급, 미채택)

*   AAC 오프라인 연동 — 스키마 확장 지점만 유지 (v0.1 9.2)

## 2\. 시스템 아키텍처

### 2.1 구성

```
        [ PWA (설치형 웹앱) ]
              │  HTTPS / JWT
              ▼
   ┌──────────────────────┐        ┌──────────────────────┐
   │  Spring Boot (Main)  │◄─REST─►│   FastAPI (AI/ML)    │
   │  인증 · CRUD · 트랜잭션  │        │ 루틴생성 · 추천 · 판정 · 챗봇 │
   └──────────┬───────────┘        └──────────┬───────────┘
              │ 읽기+쓰기 (Flyway 소유)           │ 읽기 전용
              │                                │ + adjustments INSERT
              ▼                                ▼
           ┌────────────────────────────────────┐
           │          PostgreSQL                │
           └────────────────────────────────────┘
                            │
        외부: OpenAI · 카카오맵 JS SDK · Google Calendar · Web Push
```

### 2.2 컴포넌트 책임 — \[변경\]

v0.1 표에 두 줄이 추가된다.

| 컴포넌트 | 추가된 책임 | 여전히 하지 않는 것 |
| --- | --- | --- |
| 클라이언트 (PWA) | **현재 위치 1회 조회, 등록 장소와의 거리 계산, Web Push 수신, 서비스워커 캐싱** | 판정 로직, 난이도 계산, **좌표의 서버 전송** |
| FastAPI | **챗봇 세션 처리 + 루틴 수정안 생성** | 스키마 변경, 일반 테이블 쓰기 (챗봇도 예외 아님 — 6.5) |

**거리 계산을 클라이언트에 두는 것이 핵심 설계 결정이다.** 서버가 판정하려면 좌표를 올려야 하는데, 브라우저 안에서 하버사인 몇 줄로 끝나는 계산이다. 좌표가 기기 밖으로 나가지 않으므로 개인정보 부담이 사라지고 서버에 공간 연산도 필요 없어진다. PostGIS 미채택 판단(v0.1 3장)이 그대로 유지된다.

### 2.3 서비스 경계 — \[변경 없음\]

v0.1 2.3 그대로. FastAPI는 `GRANT SELECT` + `adjustments` INSERT만. 난이도 조정의 유일한 입구는 `adjustments` INSERT이고 트리거가 적용한다. psql 시연 경로도 유지된다.

### 2.4 클라이언트 기술 — **\[확정\]**

**PWA로 확정한다.** 근거는 배포다. 스토어 심사 없이 URL 하나로 심사위원·테스터에게 전달되고, 수정이 즉시 반영된다. 일정이 8/7 착수인 프로젝트에서 이 차이는 크다.

이 결정으로 **포기하는 것을 명시해 둔다.** 나중에 "왜 안 되지"로 되돌아오지 않기 위해서다.

| 기능 | PWA | 대응 |
| --- | --- | --- |
| 앱 종료 상태에서 위치 진입 자동 감지 | **불가** | 3.1의 세 경로로 대체 |
| 홈 화면 위젯 | **불가** | 범위 밖 (1.3) |
| OS 캘린더 직접 읽기 | **불가** | Google Calendar OAuth (5.5) |
| 백그라운드 위치 추적 | **불가** | 하지 않는다. 애초에 배터리·프라이버시 비용이 크다 |
| 위치 조회 (앱 사용 중) | 가능 | `navigator.geolocation` |
| 푸시 알림 | 가능 (조건부) | iOS는 홈 화면 추가 필요 — 3.3 |
| 오프라인 동작 | 가능 | 서비스워커 |

**서비스워커는 위치 API에 접근할 수 없다.** Periodic Background Sync도 마찬가지다. 백그라운드 지오펜싱은 어떤 우회로도 없으므로 설계에서 제외한다.

## 3\. 위치 기반 루틴 — **\[신규\]**

메인으로 승격된 기능이므로 장을 따로 둔다. **PWA 제약 안에서 성립하는 형태로 설계했다.**

### 3.1 세 개의 경로

회의에서 나온 요구는 두 가지였다 — "플래너의 장소 데이터를 받아 루틴을 배치한다"와 "집/회사/헬스장 루틴이 따로 있다". 앞의 것이 원래 발언에 더 가깝고, **그건 위치 권한 없이 서버에서 전부 된다.**

**A. 일정 장소 기반 배치 — 위치 권한 불필요 · 우선순위 1**

```
캘린더 일정의 장소 문자열 ("강남 헬스장", "회사")
   → 루틴 설계 시 AI 입력에 포함
   → 해당 시간대에 그 장소에서 할 수 있는 action 우선 배치
```

순수 서버 로직이다. 브라우저도, 권한도, GPS도 필요 없다. **위치 기반 기능의 본체가 여기 있고, 회의에서 "이벤트만 추가되는 거라 어렵지 않다"고 한 것도 이 얘기다.**

**B. 앱 진입 시 현재 위치 매칭 — 위치 권한 필요 · 우선순위 2**

```
사용자가 앱을 연다
   → navigator.geolocation.getCurrentPosition() 1회
   → 로컬에 캐시된 places 목록과 거리 계산 (하버사인)
   → 반경 안이면 그 장소 루틴 카드를 상단에 노출
   → POST /places/{id}/enter  (좌표 아님, 장소 id만)
```

"헬스장에 도착해서 앱을 열면 헬스장 루틴이 떠 있다." 자동 알림은 없지만 **체감 가치의 대부분이 여기서 나온다.** 사용자는 어차피 루틴을 하려고 앱을 연다.

**C. 시간 패턴 기반 푸시 — Phase 2**

`place_visits`가 쌓이면 "평일 9시엔 보통 회사"를 학습해 Web Push로 미리 알린다. **위치 권한 없이 동작한다.** 자동 진입 감지의 실질적 대체재이고, 데이터가 쌓인 뒤에나 의미가 있으므로 Phase 2다.

> **정리** — A가 본체, B가 체감, C가 나중. 셋 중 어느 것도 백그라운드 위치를 쓰지 않는다.

### 3.2 스키마 확장 — \[검토\]

v0.5의 6테이블에 2개가 추가된다.

```sql
-- 사용자가 지정한 장소
create table places (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references users(id) on delete cascade,
  label       text not null,              -- '집' '회사' '헬스장'
  lat         double precision not null,
  lng         double precision not null,
  radius_m    integer not null default 300 check (radius_m between 100 and 2000),
  kakao_place_id text,                    -- 카카오 Local 검색 결과 id (nullable)
  archived_at timestamptz,
  created_at  timestamptz not null default now()
);

-- 장소 매칭 이벤트. 서브기능 '장소 피드백'의 입력이기도 하다
create table place_visits (
  id         bigserial primary key,
  user_id    uuid not null references users(id) on delete cascade,
  place_id   uuid not null references places(id),
  entered_at timestamptz not null default now()
);
```

`routines`에 `place_id uuid references places(id)` 컬럼을 추가한다. **nullable이다** — 시간 기반 루틴과 장소 기반 루틴이 공존한다.

`radius_m` 기본값을 300m로 잡은 것은 브라우저 Geolocation의 정확도가 네이티브보다 낮기 때문이다. 실내에서는 Wi-Fi 측위로 떨어져 오차가 수백 미터까지 벌어진다. 좁게 잡으면 헬스장 안에 있는데도 매칭이 안 된다.

`place_visits`는 **앱을 열었을 때만 기록된다.** 장소 피드백 서브기능("또 술집에 가셨군요")의 커버리지가 완전하지 않다는 뜻이고, 이건 PWA 선택의 직접적 귀결이다. Phase 2 설계 시 이 한계를 전제로 문구를 잡아야 한다 — 방문 횟수를 단정하는 표현("이번 주 3번")은 쓸 수 없고, 관찰된 것만 말해야 한다.

### 3.3 알아둘 제약

| 제약 | 내용 | 대응 |
| --- | --- | --- |
| Secure context | Geolocation·푸시 모두 HTTPS 필수 | 로컬 개발은 `localhost` 예외 사용 |
| 위치 권한 | 거부 가능, 브라우저별 재요청 정책 상이 | 거부 시 경로 A만으로 동작 (9.1) |
| 정확도 | 실내 측위 오차 수백 m | `radius_m` 기본 300 |
| **iOS 푸시** | **홈 화면 추가(A2HS) 후에만 가능, iOS 16.4+** | 온보딩에 "홈 화면에 추가" 안내 단계 필수 |
| 서비스워커 | 위치 API 접근 불가 | 백그라운드 감지 설계 제외 (2.4) |
| iOS 저장소 | 미사용 시 브라우저가 캐시를 정리할 수 있음 | 중요한 상태는 서버에 둔다 |

**iOS 푸시 조건이 실질적 리스크다.** 홈 화면에 추가하지 않은 iPhone 사용자는 알림을 아예 받지 못한다. 온보딩에서 A2HS를 유도하는 화면이 없으면 iOS 사용자의 리마인드 경로가 통째로 사라진다.

## 4\. 데이터 설계

v0.5(`hq-db-design.md`) 기준. 3.2의 2테이블 추가 외에 변경 없다.

| 층 | 대상 | 대응 기능 |
| --- | --- | --- |
| 정의 | `actions` `routines` `routine_tasks` `places` | ① 루틴 설계 ② 위치 기반 |
| 실행 | `task_logs` `place_visits` | 최소 입력 원칙 |
| 판정 | `v_daily_states` `adjustments` | ④ 이상치 패턴 ⑤ 점진적 복귀 |

v0.1 4.2의 세 원칙(난이도 = 사다리 좌표 / 과거 기록 동결 / 판정 결과 미저장)은 그대로 유효하다. 4.3 인가 원칙 — RLS를 쓰지 않으므로 **모든 조회에** `userId` **강제**, 통합 테스트에 타인 데이터 조회 케이스 포함 — 도 유효하며, `places`가 추가되면서 **더 중요해졌다.** 집·직장 좌표는 유출 시 피해가 가장 큰 데이터다.

## 5\. API 설계 — \[검토\]

### 5.1 인증과 게스트 모드 — **\[신규·미결\]**

회의에서 게스트 시작을 유지하기로 했으나, **메인 기능(루틴 생성)이 데이터 수집 동의를 요구하므로 게스트가 볼 수 있는 것이 정의되지 않았다.** 기능 목록은 다 보이는데 누를 때마다 회원가입을 요구하는 화면은 이탈 방지가 아니라 이탈 사유다.

기술적으로 가장 싼 해법을 제안한다.

**\[검토\] 게스트는 완전 로컬. 서버에 아무 흔적도 남기지 않는다.**

|  | 게스트 | 회원 |
| --- | --- | --- |
| 샘플 루틴 체험 | 브라우저 로컬 저장소 1개 | — |
| 루틴 생성·저장 | ✕ (회원가입 유도) | ○ |
| 위치·캘린더·AI | ✕ | ○ |
| 서버 레코드 | **없음** | `users` 행 생성 |

게스트 계정을 서버에 만들면 익명 사용자 테이블, 가입 시 데이터 이관, 미전환 계정 정리가 전부 따라온다. **로컬 전용으로 두면 백엔드 작업량이 0이다.** 전환 시점에 이관할 데이터가 샘플 하나뿐이라 버려도 된다.

인증 자체는 v0.1 5.1 그대로 — OAuth(kakao/google) 인가 코드를 클라이언트가 받아 `POST /auth/{provider}`로 교환, Spring이 자체 JWT 발급. JWT `sub` = `users.id`. **\[미결\]** refresh 정책은 여전히 미정.

> 회의 중 "OAuth가 곧 구글 로그인인가"라는 혼선이 있었다. OAuth 2.0은 **인가 프로토콜 표준**이고 구글·카카오·애플이 각각 그 표준을 구현한 제공자다. 문서에는 `provider` 파라미터로 구분해 적는다.

### 5.2 주요 엔드포인트 (Spring Boot)

v0.1 5.2에 아래가 추가된다.

## 6\. AI 파이프라인

### 6.1 원칙 — \[변경 없음\]

생성형보다 **기존 데이터 기반 추천 우선.** LLM은 자유 생성이 아니라 `actions` 라이브러리에서 고르고 이유를 설명하는 역할. Structured Outputs로 출력 스키마를 강제해 존재하지 않는 action 생성을 차단한다.

### 6.2 ~ 6.4 — \[변경 없음\]

루틴 설계·이상치 감지·점진적 복귀는 v0.1 6.2~6.4가 그대로 유효하다. 루틴 설계 입력에 **3.1-A의 일정 장소 문자열**이 추가된다. **\[미결\]** Green/Yellow/Red 컷오프와 `gray` 상태 도입은 여전히 미정이다.

### 6.5 챗봇 — **\[신규\]**

회의에서 확정된 요구는 두 가지다. **루틴 설명**과 **자연어 수정**("이렇게 바꾸고 싶어" → 자동 반영).

```
사용자 발화
  → 컨텍스트 조립 (현재 루틴 + 최근 7일 상태 + actions 후보)
  → LLM (Structured Outputs)
  → 응답 유형 분기
       ├ 설명형   → 텍스트만 반환
       └ 수정형   → { intent, target_task_id, proposed_action_id, reason }
                     → 클라이언트가 사용자에게 확인 → 확인 시 Spring이 저장
```

**LLM 출력이 DB에 직접 반영되지 않는다.** 제안을 구조화해 돌려주고, 저장은 사용자 확인 후 Spring이 한다. 이유는 셋이다 — 잘못된 수정의 되돌리기 비용, FastAPI 쓰기 권한 제약(2.3), 그리고 프롬프트 인젝션(7.2).

### 6.6 AI가 DB를 읽는 방식 — **\[결정 필요\]**

회의에서 "마크다운 표로 변환해 전달" vs "FAISS로 다 읽힌다" 두 안이 나왔고 **결론 없이 넘어갔다.** 8/7에 백엔드가 바로 부딪히는 결정이라 여기서 답을 제안한다.

**\[검토\] 마크다운/JSON 직렬화. FAISS는 도입하지 않는다.**

v0.1 9.1이 이미 같은 결론을 냈고, 이번 회의로 근거가 더 강해졌다.

|  | 규모 | 결론 |
| --- | --- | --- |
| `actions` 라이브러리 | 수십 행 | `category` + `ladder_key` 필터로 충분 |
| 사용자 루틴 | 수~수십 행 | 통째로 프롬프트에 넣어도 컨텍스트 여유 |
| 최근 상태 | 7~14행 | 집계 후 표 한 개 |

벡터 검색은 **후보가 너무 많아 다 못 넣을 때** 쓰는 도구다. HQ는 후보가 적다. 인덱스 생성·저장·동기화 비용이 시연 일정 안에 회수되지 않는다. 나중에 정말 필요해지면 **pgvector**로 PostgreSQL 안에서 해결하면 되고, 그때도 인프라는 늘지 않는다.

LangChain도 같은 질문을 받는다. 파이프라인이 이 정도 단계 수라면 OpenAI SDK 직접 호출이 디버깅하기 쉽다. 도입한다면 "무엇을 대신 해주는가"를 답할 수 있어야 한다.

### 7.1 성능

| 항목 | 수단 |

| 첫 화면 로딩 | 서비스워커로 셸 캐싱. **PWA는 첫 진입 체감이 네이티브 대비 불리하다** |
| 위치 조회 | **진입 시 1회만.** `watchPosition` 상시 구독 금지 |

`watchPosition`을 금지하는 이유는 배터리다. PWA에서도 앱이 열려 있는 동안은 계속 GPS를 물고 있게 되고, 이건 사용자가 체감한다. 3.1-B는 1회 조회로 충분하다.

### 7.2 보안 — \[변경\]

| 항목 | 수단 |
| --- | --- |
| 인가 | Spring Security. 모든 조회에 `userId` 강제 (4장) |
| DB 권한 분리 | FastAPI 롤은 SELECT + `adjustments` INSERT만 |
| **API 키** | **카카오 JS 키는 도메인 등록. REST 키·OpenAI 키는 서버 전용** |
| **토큰 저장** | **JWT를** `localStorage`**에 두지 않는다 — XSS에 그대로 노출된다.** httpOnly 쿠키 **\[검토\]** |
| **프롬프트 인젝션** | 아래 참조 |
| 전송 | 전 구간 HTTPS (PWA 필수 조건이기도 하다) |

**웹이라서 XSS 노출면이 생긴다.** 네이티브였다면 없었을 항목이고, PWA 선택의 직접적 비용이다. 토큰을 httpOnly 쿠키에 두면 CSRF 대책(SameSite)이 따라오지만, `localStorage`보다 안전하다.

**프롬프트 인젝션에 대해.** 회의에서 "제한은 걸 수 있지만 작정하고 우회하면 방어가 어렵다, 그럴 사람은 없을 것"이라는 판단이 나왔다. 리스크 수용 자체는 데모 단계에서 합리적이다. 다만 **완화 수단이 공짜인 것 두 가지는 그냥 넣는다.**

1.  **챗봇에 쓰기 권한을 주지 않는다** (6.5). 인젝션이 성공해도 얻는 것이 텍스트뿐이다
    
2.  `proposed_action_id`**가 실제** `actions`**에 존재하고 그 사용자 루틴 소속인지 서버가 검증**한다. LLM이 뭘 뱉든 스키마 밖으로 못 나간다
    

이 둘은 방어 목적이 아니라 **정상 동작에도 필요한 검증**이라 추가 비용이 없다. 실질적 위험은 인젝션보다 **다른 사용자 데이터가 컨텍스트에 섞여 들어가는 것**이고, 그건 4장의 `userId` 강제로 막는다.

### 7.3 개인정보 — **\[확대\]**

| 데이터 | 민감도 | 수집 방식 | 상태 |
| --- | --- | --- | --- |
| 지정 장소 좌표 | **높음** | 사용자가 직접 등록. 집·직장 위치 | \[검토\] |
| 현재 위치 | 높음 | **기기 밖으로 나가지 않음** (2.2) | \[검토\] |
| 장소 방문 이력 | 중간 | 장소 id + 시각만 | \[검토\] |
| 캘린더 일정 | 높음 | 빈 시간대·장소만 추출, 제목 미저장 (5.5) | \[검토\] |
| 식단 이미지 | 중간 | Phase 2 | \[미결\] |

**설계로 이미 줄인 것** — 현재 위치 좌표는 브라우저 안에서만 쓰이고 서버로 가지 않으며, 캘린더는 일정 원문 대신 빈 시간대만 올린다. 기술 선택이 곧 프라이버시 대책인 사례이므로 개인정보 처리방침에 그대로 쓸 수 있다.

**\[미결·중요\]** `places`에 저장되는 집·직장 좌표는 사용자가 직접 등록한 것이지만 민감도가 가장 높다. 회의에서 약관·제3자 제공 논의를 "회원가입 페이지 만들 때"로 미뤘는데, **위치 + 캘린더 + 건강 관련 데이터를 함께 다루는 구성이면 별도 회의가 필요한 규모다.** `users.consent` jsonb에 scope별로 기록하고, 위치 동의는 다른 항목과 분리한다.

### 7.4 데이터 무결성 — \[변경 없음\]

하드 삭제 금지, `archived_at` 소프트 삭제. 삭제 연쇄는 cascade / no action (`restrict` 금지 — v0.4에서 회원 탈퇴 영구 실패 발생). `places`도 같은 정책을 따른다.

## 9\. 리스크와 미결 사항

### 9.1 기술 리스크 — \[변경\]

**위치 권한 거부가 3.1-B를 무력화한다.** 브라우저 위치 권한은 거부율이 네이티브보다 높다. **경로 A(일정 장소 기반 배치)는 권한과 무관하게 동작하므로, 위치 기능의 본체를 A에 두는 것이 그 자체로 대비책이다.** B는 증강이지 전제가 아니다.

**iOS PWA가 가장 약한 고리다.** 푸시가 A2HS에 걸려 있고(3.3), 저장소가 정리될 수 있으며, 설치 유도 UI가 Android만큼 자연스럽지 않다. **iOS 사용자 비중이 높은 심사 환경이라면 온보딩의 A2HS 안내가 기능 하나만큼 중요하다.**

**PWA의 첫인상.** 스토어 앱과 나란히 평가받으면 로딩·전환 애니메이션에서 차이가 드러난다. 서비스워커 셸 캐싱과 스켈레톤 UI로 상당 부분 가려지지만, **프론트 착수 시 이걸 나중 과제로 미루면 시연 직전에 티가 난다.**

**서브 기능 4개가 서로 다른 파이프라인이다.** 멘탈 코치·장소 피드백은 기존 자산 재사용이지만, 식단(VLM)과 캐릭터(에셋·상태관리)는 신규 구축이다. Phase 2 착수 시 이 둘은 별개 프로젝트로 취급한다.

**식단 기능의 차별성이 없다.** 회의 중 카카오 파스타를 확인하며 "저희가 말한 게 거의 다 들어가 있다"는 발언이 나왔다. 사진 기반 칼로리 분석은 이미 상용 서비스가 덮은 영역이다. **HQ의 차별점은 위치 기반 + 챗봇 수정이며, 식단은 그 뒤에 붙는 보조 기능으로 위치를 잡아야 한다.** PRD 차별점 서술에 이 논리를 명시할 것.

**OpenAI API 의존.** 루틴 생성 실패 시 `v_action_priors` 기반 규칙 추천으로 폴백하면 시연 중 API 장애에도 화면이 비지 않는다. (v0.1 9.1 유지)

**서버 2개 운영 비용.** 일정이 촉박하면 초기에는 단일 배포 단위로 묶고 경계만 코드로 유지하는 선택지가 있다. (v0.1 9.1 유지)

**FAISS·LangChain 재검토** — 6.6에서 결론을 냈다.

### 9.2 일정 리스크 — **\[신규\]**

```
8/5 (오늘)  문서 최종 → 디스코드 피드백
8/6 저녁    중간 발표 (UI/UX 피드백)

```

**8/6 저녁에 UI/UX 피드백을 받고 8/7 아침에 개발을 시작하면 반영 시간이 0이다.** 회의에서도 "백엔드는 바로 되겠는데 프론트가 회의를 좀 하면서 해야겠다"고 짚었다.

| 8/7 착수 | 대상 | 근거 |
| --- | --- | --- |
| ○ | 백엔드 — 스키마 마이그레이션, 인증, `places` CRUD | 화면과 독립 |
| ○ | AI — `actions` 시드, 루틴 생성 파이프라인 | 화면과 독립 |
| ○ | 프론트 — **PWA 셋업 + 권한 스파이크** | 화면 확정 불필요 |
| ✕ | 프론트 — 실제 화면 구현 | 8/6 피드백 반영 후 |

**권한 스파이크를 8/7에 끝내라.** 확인할 것은 셋이다.

1.  HTTPS 환경에서 `getCurrentPosition()`이 실기기에서 실제로 어느 정도 정확한가 (실내 오차 → `radius_m` 기본값 확정)
    
2.  **iOS Safari에서 홈 화면 추가 후 Web Push가 실제로 도착하는가**
    
3.  Google OAuth 동의 화면이 테스트 사용자로 통과되는가
    

셋 다 문서로는 알 수 없고 실기기로만 확인된다. 늦게 터지면 메인 기능이나 리마인드 경로가 통째로 흔들린다.

### 9.5 용어 통일 — \[변경 없음\]

기능 ④의 정식 명칭은 \*\*"이상치 패턴 감지"\*\*다. 회의록의 "이탈 신호 감지"와 DB 설계 문서의 "이상치 패턴"이 갈려 있다. PRD·TRD·SRS가 하나로 통일할 것.

'무기력증', '실행기능 저하' 등 정신건강 진단으로 오해될 표현은 모든 문서에서 사용하지 않는다. **서브 기능 '멘탈 코치'의 사용자 노출 문구에도 동일하게 적용된다.**
