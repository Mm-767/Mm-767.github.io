## 0\. v0.1에서 무엇이 바뀌었나

8/5 회의로 이 문서의 전제 세 개가 바뀌었다.

| # | v0.1 | v0.2 | 파급 |
| --- | --- | --- | --- |
| 1 | 위치 기반 = 서브 기능 후보, 범위 밖 | **위치 기반 = 메인 기능** | 클라이언트 선택이 강제된다 (2.4) |
| 2 | AI 챗봇 = 위상 미결, 범위 밖 | **챗봇 = 핵심**, 멘탈 코치를 흡수 | 6장에 파이프라인 추가, 7.2에 신규 공격면 |
| 3 | 클라이언트 = Flutter vs PWA 미결·최우선 | **PWA 탈락** — 1번의 기술적 귀결 | 5.4 캘린더 연동 방식도 함께 결정됨 |

②이상치 패턴 감지와 ③점진적 복귀는 이번 회의에서 부정되지 않았다. v0.1의 4·6장이 그대로 유효하다.

## 1\. 개요와 범위

### 1.1 목적

v0.1과 동일하다. 무엇을 만들지는 PRD, 만족 조건은 SRS, **구현 수단**만 이 문서가 다룬다.

### 1.2 대상 기능 — **\[변경\]**

8/5 회의에서 메인/서브 경계가 다시 그어졌다.

**메인 (Phase 1 — 8/7 개발 시작 대상)**

| 기능 | 상태 | 이 문서에서 다루는 범위 |
| --- | --- | --- |
| ① AI 루틴 설계 | \[확정\] | 2·5·6장 |
| ② 위치 기반 루틴 트리거 | **\[확정·신규\]** | 3장 전체 |
| ③ 일정/캘린더 연동 | \[확정\] | 5.5 |
| ④ 이상치 패턴 감지 (Green/Yellow/Red) | \[확정\] | v0.1 6.3 유효 |
| ⑤ 점진적 루틴 복귀 | \[확정\] | v0.1 6.4 유효 |
| ⑥ AI 챗봇 (루틴 설명 + 자연어 수정) | **\[확정·승격\]** | 6.5 |

**서브 (Phase 2 — 구현 못 하면 드롭)**

| 순위 | 기능 | 기술 재사용 | 신규 비용 |
| --- | --- | --- | --- |
| 1 | AI 멘탈 코치 | 챗봇 그대로 (프롬프트 + 트리거 조건만 추가) | 거의 없음 |
| 2 | 장소 피드백 | ②의 방문 로그 재사용 | 낮음 |
| 3 | 식단 기록 | — | **VLM 파이프라인 신규** |
| 4 | 캐릭터 | — | 디자인 에셋 + 상태 관리 신규 |

앞의 둘은 이미 만드는 것에 얹는 것이고, 뒤의 둘은 새로 파는 것이다. 회의에서 정해진 우선순위와 기술 비용 순서가 일치한다.

> **PRD 작성 시 주의** — 서브 4개를 메인과 같은 층에 나열하면 코드 생성 도구가 4개를 모두 스캐폴딩한다. "구현 못 하면 드롭"은 사람의 의도이지 도구의 동작이 아니다. 문서상 **Phase 2로 물리적으로 분리**할 것.

## 2\. 시스템 아키텍처

### 2.1 구성 — \[변경 없음, 클라이언트만 확정\]

```
        [ Flutter (Android 우선) ]
              │  HTTPS / JWT
              ▼
   ┌──────────────────────┐        ┌──────────────────────┐
   │  Spring Boot (Main)  │◄─REST─►│   FastAPI (AI/ML)    │
   │  인증 · CRUD · 트랜잭션  │        │ 루틴생성 · 추천 · 판정 · 챗봇 │
   └──────────┬───────────┘        └──────────┬───────────┘
              │ 읽기+쓰기 (Flyway 소유)           │ 읽기 전용
              │                                │ + adjustments INSERT
              ▼                                ▼
           ┌────────────────────────────────────┐
           │          PostgreSQL                │
           └────────────────────────────────────┘
                            │
          외부: OpenAI · 카카오맵 Local · OS 캘린더(온디바이스)
```

### 2.2 컴포넌트 책임 — \[변경\]

v0.1 표에 두 줄이 추가된다.

| 컴포넌트 | 추가된 책임 | 여전히 하지 않는 것 |
| --- | --- | --- |
| 클라이언트 | **지오펜스 등록·감지, 위치 권한 관리, OS 캘린더 읽기, 로컬 알림** | 판정 로직, 난이도 계산, 원시 위치 좌표의 상시 서버 전송 |
| FastAPI | **챗봇 세션 처리 + 루틴 수정안 생성** | 스키마 변경, 일반 테이블 쓰기 (챗봇도 예외 아님 — 6.5 참조) |

지오펜스 판정을 **클라이언트에 두는 것이 핵심 설계 결정**이다. 서버가 좌표를 계속 받아 판정하려면 위치를 상시 업로드해야 하고, 그건 배터리·통신비·개인정보 세 방향에서 전부 비싸다. OS가 제공하는 지오펜싱은 저전력 하드웨어 경로를 쓰므로, **진입 이벤트가 발생한 순간에만** 서버로 한 건 보낸다.

### 2.3 서비스 경계 — \[변경 없음\]

v0.1 2.3 그대로. FastAPI는 `GRANT SELECT` + `adjustments` INSERT만. 난이도 조정의 유일한 입구는 `adjustments` INSERT이고 트리거가 적용한다. psql 시연 경로도 유지된다.

### 2.4 클라이언트 기술 — **\[변경 · 미결 해소\]**

v0.1에서 이 항목은 "미결·최우선"이었다. **8/5 회의에서 위치 기반을 메인으로 올린 순간 기술적으로 답이 정해졌다.**

| 요구 | Flutter (네이티브) | PWA |
| --- | --- | --- |
| **백그라운드 지오펜싱** | OS API 제공 | **불가** |
| 앱 종료 상태에서 진입 감지 | 가능 | **불가** |
| 위젯 | 가능 | 불가 |
| OS 캘린더 읽기 | 플러그인으로 가능 | 불가 (OAuth 별도 필요) |
| 시연 | APK 설치 | URL 하나 |

PWA를 고르면 "회사에 도착하면 회사 루틴이 뜬다" — 이번 회의의 핵심 기능이 **성립하지 않는다.** 앱을 열어 수동 새로고침해야 위치를 읽는다. 메인 기능을 포기하지 않는 한 선택지는 하나다.

**→ \[검토\] Flutter, Android 우선, iOS는 Phase 2로 미룬다.**

iOS를 미루는 이유는 세 가지다. 백그라운드 위치 권한이 심사에서 사용 목적 소명을 요구하고, 지오펜스 등록 상한이 20개(Android는 100개)이며, 배포에 개발자 계정과 심사 기간이 든다. 심사·시연이 목적이라면 **APK 직배포가 가장 싼 경로**다.

> 이 결정은 아직 팀 승인 전이다. 8/6 중간 발표에서 확정해야 8/7 프론트 착수가 가능하다.

## 3\. 위치 기반 루틴 트리거 — **\[신규\]**

메인으로 승격된 기능이므로 장을 따로 둔다.

### 3.1 동작 흐름

```
[등록]  사용자가 장소 지정 (카카오맵 검색 or 지도 핀)
          → places INSERT (label, lat, lng, radius_m)
          → 루틴에 place_id 연결
          → 클라이언트가 OS에 지오펜스 등록

[감지]  OS가 진입/이탈 감지 (앱 종료 상태 포함)
          → 클라이언트 콜백 기동
          → POST /places/{id}/enter  (좌표 아님, 장소 id만)
          → 서버가 해당 장소 루틴 반환
          → 로컬 알림 + 오늘 목록 상단 노출
```

**서버로 좌표를 보내지 않는다.** 클라이언트가 보내는 것은 "몇 번 장소에 들어왔다"는 사실뿐이다. 개인정보 노출면을 줄이는 가장 값싼 방법이고, 서버에 공간 연산이 필요 없어져 PostGIS 미채택 판단(v0.1 3장)도 그대로 유지된다.

### 3.2 스키마 확장 — \[검토\]

v0.5의 6테이블에 2개가 추가된다.

```sql
-- 사용자가 지정한 장소
create table places (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references users(id) on delete cascade,
  label       text not null,              -- '집' '회사' '헬스장'
  lat         double precision not null,
  lng         double precision not null,
  radius_m    integer not null default 150 check (radius_m between 100 and 1000),
  kakao_place_id text,                    -- 카카오 Local 검색 결과 id (nullable)
  archived_at timestamptz,
  created_at  timestamptz not null default now()
);

-- 진입 이벤트. 서브기능 '장소 피드백'의 입력이기도 하다
create table place_visits (
  id         bigserial primary key,
  user_id    uuid not null references users(id) on delete cascade,
  place_id   uuid not null references places(id),
  entered_at timestamptz not null default now()
);
```

`routines`에 `place_id uuid references places(id)` 컬럼을 추가한다. **nullable이다** — 시간 기반 루틴과 장소 기반 루틴이 공존한다.

`radius_m` 하한을 100m로 둔 것은 GPS 오차와 OS 지오펜싱의 실질 정밀도 때문이다. 그보다 작게 잡으면 진입 이벤트가 누락되거나 반복 발화한다.

### 3.3 알아둘 제약

| 제약 | 값 | 대응 |
| --- | --- | --- |
| 지오펜스 등록 상한 | Android 100 / iOS 20 | 활성 장소만 등록, 상한 도달 시 최근 방문 순 |
| 진입 감지 지연 | 수십 초~수 분 | 즉시성을 요구하는 UX를 설계하지 않는다 |
| 재부팅 후 소실 | 등록 해제됨 | BOOT\_COMPLETED 수신 후 재등록 |
| 권한 | Android 10+ 는 "항상 허용" 별도 요청 | 온보딩에서 이유를 설명하고 단계적으로 요청 |

**"항상 허용" 권한은 사용자가 거부할 수 있다.** 거부 시 위치 기능만 비활성화되고 나머지 루틴 기능은 정상 동작해야 한다. 메인 기능이 권한 하나에 전부 걸리지 않도록 폴백을 반드시 둔다.

## 5\. API 설계 — \[검토\]

### 5.1 인증과 게스트 모드 — **\[신규·미결\]**

회의에서 게스트 시작을 유지하기로 했으나, **메인 기능(루틴 생성)이 데이터 수집 동의를 요구하므로 게스트가 볼 수 있는 것이 정의되지 않았다.** 기능 목록은 다 보이는데 누를 때마다 회원가입을 요구하는 화면은 이탈 방지가 아니라 이탈 사유다.

기술적으로 가장 싼 해법을 제안한다.

**\[검토\] 게스트는 완전 로컬. 서버에 아무 흔적도 남기지 않는다.**

|  | 게스트 | 회원 |
| --- | --- | --- |
| 샘플 루틴 체험 | 로컬 저장소 1개 | — |
| 루틴 생성·저장 | ✕ (회원가입 유도) | ○ |
| 위치·캘린더·AI | ✕ | ○ |
| 서버 레코드 | **없음** | `users` 행 생성 |

게스트 계정을 서버에 만들면 익명 사용자 테이블, 가입 시 데이터 이관, 미전환 계정 정리가 전부 따라온다. **로컬 전용으로 두면 백엔드 작업량이 0이다.** 전환 시점에 이관할 데이터가 샘플 하나뿐이라 버려도 된다.

인증 자체는 v0.1 5.1 그대로 — OAuth(kakao/google) 인가 코드를 클라이언트가 받아 `POST /auth/{provider}`로 교환, Spring이 자체 JWT 발급. JWT `sub` = `users.id`. **\[미결\]** refresh 정책은 여전히 미정.

> 회의 중 "OAuth가 곧 구글 로그인인가"라는 혼선이 있었다. OAuth 2.0은 **인가 프로토콜 표준**이고 구글·카카오·애플이 각각 그 표준을 구현한 제공자다. 문서에는 `provider` 파라미터로 구분해 적는다.

### 5.2 주요 엔드포인트 (Spring Boot)

v0.1 5.2에 아래가 추가된다.

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| `GET` `POST` | `/places` | 장소 목록 / 등록 |
| `PATCH` `DELETE` | `/places/{id}` | 수정 / 보관 |
| `POST` | `/places/{id}/enter` | **진입 이벤트 기록 + 해당 장소 루틴 반환** |
| `GET` | `/places/search?q=` | 카카오 Local 프록시 (키 노출 방지) |
| `POST` | `/chat` | 챗봇 대화 (6.5) |

`/places/search`를 서버 프록시로 두는 이유는 카카오 API 키를 클라이언트에 넣지 않기 위해서다. Flutter 앱은 디컴파일이 어렵지 않다.

### 5.3 서버 간 통신 — \[변경\]

v0.1 3개에 하나 추가.

| 메서드 | 경로 | 요청 | 응답 |
| --- | --- | --- | --- |
| `POST` | `/ai/chat` | 세션 id, 발화, 루틴 컨텍스트 | 답변 + **선택적 수정 제안(구조화)** |

### 5.4 외부 연동 — \[변경\]

| 대상 | 용도 | 상태 |
| --- | --- | --- |
| OpenAI API | 루틴 생성, 챗봇, 패턴 요약 (Structured Outputs) | \[검토\] |
| 카카오맵 Local | 장소 검색 (서버 프록시) | \[검토\] |
| **OS 캘린더 (온디바이스)** | 일정 읽기 | **\[검토·변경\]** |
| VLM (식단 이미지) | Phase 2 | \[미결\] |

### 5.5 캘린더 연동 — **\[변경\]**

v0.1에서 "연동 대상 서비스 미정 \[미결\]"이었다. Flutter 확정으로 **가장 싼 경로가 생겼다.**

Google Calendar API를 쓰려면 별도 OAuth 스코프, 동의 화면 심사, 토큰 갱신, 서버 저장이 전부 붙는다. 반면 **OS 캘린더를 온디바이스로 읽으면** 구글·애플·네이버 등 기기에 등록된 캘린더를 **한 번에** 얻는다. 사용자가 이미 쓰는 캘린더가 무엇이든 상관없어진다.

**\[검토\] 온디바이스 캘린더 읽기 전용.** 일정 원문을 서버에 올리지 않고, 루틴 배치에 필요한 **빈 시간대와 장소 문자열만** 추출해 전송한다. 7.3의 개인정보 부담이 크게 줄어든다.

## 6\. AI 파이프라인

### 6.1 원칙 — \[변경 없음\]

생성형보다 **기존 데이터 기반 추천 우선.** LLM은 자유 생성이 아니라 `actions` 라이브러리에서 고르고 이유를 설명하는 역할. Structured Outputs로 출력 스키마를 강제해 존재하지 않는 action 생성을 차단한다.

### 6.2 ~ 6.4 — \[변경 없음\]

루틴 설계·이상치 감지·점진적 복귀는 v0.1 6.2~6.4가 그대로 유효하다. **\[미결\]** Green/Yellow/Red 컷오프와 `gray` 상태 도입은 여전히 미정이다.

### 6.5 챗봇 — **\[신규\]**

회의에서 확정된 요구는 두 가지다. **루틴 설명**과 **자연어 수정**("이렇게 바꾸고 싶어" → 자동 반영).

```
사용자 발화
  → 컨텍스트 조립 (현재 루틴 + 최근 7일 상태 + actions 후보)
  → LLM (Structured Outputs)
  → 응답 유형 분기
       ├ 설명형   → 텍스트만 반환
       └ 수정형   → { intent, target_task_id, proposed_action_id, reason }
                     → 클라이언트가 사용자에게 확인 → 확인 시 Spring이 저장
```

**LLM 출력이 DB에 직접 반영되지 않는다.** 제안을 구조화해 돌려주고, 저장은 사용자 확인 후 Spring이 한다. 이유는 셋이다 — 잘못된 수정의 되돌리기 비용, FastAPI 쓰기 권한 제약(2.3), 그리고 프롬프트 인젝션(7.2).

### 6.6 AI가 DB를 읽는 방식 — **\[결정 필요\]**

회의에서 "마크다운 표로 변환해 전달" vs "FAISS로 다 읽힌다" 두 안이 나왔고 **결론 없이 넘어갔다.** 8/7에 백엔드가 바로 부딪히는 결정이라 여기서 답을 제안한다.

**\[검토\] 마크다운/JSON 직렬화. FAISS는 도입하지 않는다.**

v0.1 9.1이 이미 같은 결론을 냈고, 이번 회의로 근거가 더 강해졌다.

|  | 규모 | 결론 |
| --- | --- | --- |
| `actions` 라이브러리 | 수십 행 | `category` + `ladder_key` 필터로 충분 |
| 사용자 루틴 | 수~수십 행 | 통째로 프롬프트에 넣어도 컨텍스트 여유 |
| 최근 상태 | 7~14행 | 집계 후 표 한 개 |

벡터 검색은 **후보가 너무 많아 다 못 넣을 때** 쓰는 도구다. HQ는 후보가 적다. 인덱스 생성·저장·동기화 비용이 시연 일정 안에 회수되지 않는다. 나중에 정말 필요해지면 **pgvector**로 PostgreSQL 안에서 해결하면 되고, 그때도 인프라는 늘지 않는다.

LangChain도 같은 질문을 받는다. 파이프라인이 이 정도 단계 수라면 OpenAI SDK 직접 호출이 디버깅하기 쉽다. 도입한다면 "무엇을 대신 해주는가"를 답할 수 있어야 한다.

### 7.2 보안 — \[변경\]

v0.1 7.2에 두 항목이 추가된다.

| 항목 | 수단 |
| --- | --- |
| 인가 | Spring Security. 모든 조회에 `userId` 강제 (4장) |
| DB 권한 분리 | FastAPI 롤은 SELECT + `adjustments` INSERT만 |
| **API 키** | **카카오·OpenAI 키는 서버 전용. 클라이언트에 두지 않는다** |
| **프롬프트 인젝션** | **아래 참조** |
| 전송 | 전 구간 HTTPS |
| 토큰 | JWT 서명 검증, 만료 정책 **\[미결\]** |

**프롬프트 인젝션에 대해.** 회의에서 "제한은 걸 수 있지만 작정하고 우회하면 방어가 어렵다, 그럴 사람은 없을 것"이라는 판단이 나왔다. 리스크 수용 자체는 데모 단계에서 합리적이다. 다만 **완화 수단이 공짜인 것 두 가지는 그냥 넣는다.**

1.  **챗봇에 쓰기 권한을 주지 않는다** (6.5). 인젝션이 성공해도 얻는 것이 텍스트뿐이다
    
2.  `proposed_action_id`**가 실제** `actions`**에 존재하고 그 사용자 루틴 소속인지 서버가 검증**한다. LLM이 뭘 뱉든 스키마 밖으로 못 나간다
    

이 둘은 방어 목적이 아니라 **정상 동작에도 필요한 검증**이라 추가 비용이 없다. 실질적 위험은 인젝션보다 **다른 사용자 데이터가 컨텍스트에 섞여 들어가는 것**이고, 그건 4장의 `userId` 강제로 막는다.

### 7.3 개인정보 — **\[대폭 확대\]**

v0.1 대비 수집 항목이 크게 늘었다. 이 장은 더 이상 뒤로 미룰 수 있는 항목이 아니다.

**설계로 이미 줄인 것** — 좌표를 서버에 안 올리고, 일정 원문을 서버에 안 올린다. 두 결정이 동의 범위와 유출 시 피해를 동시에 줄인다. 기술 선택이 곧 프라이버시 대책인 사례이므로 개인정보 처리방침에 그대로 쓸 수 있다.

**\[미결·중요\]** 위치 이력은 대부분의 국내 서비스에서 별도 동의 대상이다. 회의에서 약관·제3자 제공 논의를 "회원가입 페이지 만들 때"로 미뤘는데, **위치 + 식단 + 건강 관련 데이터를 함께 다루는 구성이면 별도 회의가 필요한 규모다.** `users.consent` jsonb에 scope별로 기록하고, 위치 동의는 다른 항목과 분리한다.

## 9\. 리스크와 미결 사항

### 9.1 기술 리스크 — \[변경\]

**위치 권한 거부가 메인 기능을 무력화한다.** Android "항상 허용"은 사용자가 거부할 수 있고, 이후 OS가 사용 빈도에 따라 자동 회수하기도 한다. **위치 없이도 시간 기반 루틴이 완전히 동작하도록** 설계한다. 위치는 증강이지 전제가 아니다.

**서브 기능 4개가 서로 다른 파이프라인이다.** 멘탈 코치·장소 피드백은 기존 자산 재사용이지만, 식단(VLM)과 캐릭터(에셋·상태관리)는 신규 구축이다. Phase 2 착수 시 이 둘은 별개 프로젝트로 취급한다.

**식단 기능의 차별성이 없다.** 회의 중 카카오 파스타를 확인하며 "저희가 말한 게 거의 다 들어가 있다"는 발언이 나왔다. 사진 기반 칼로리 분석은 이미 상용 서비스가 덮은 영역이다. **HQ의 차별점은 위치 기반 + 챗봇 수정이며, 식단은 그 뒤에 붙는 보조 기능으로 위치를 잡아야 한다.** PRD 차별점 서술에 이 논리를 명시할 것.

**OpenAI API 의존.** 루틴 생성 실패 시 `v_action_priors` 기반 규칙 추천으로 폴백하면 시연 중 API 장애에도 화면이 비지 않는다. (v0.1 9.1 유지)

**서버 2개 운영 비용.** 일정이 촉박하면 초기에는 단일 배포 단위로 묶고 경계만 코드로 유지하는 선택지가 있다. (v0.1 9.1 유지)

**FAISS·LangChain 재검토** — 6.6에서 결론을 냈다.

### 9.2 일정 리스크 — **\[신규\]**

### 9.5 용어 통일 — \[변경 없음\]

기능 ④의 정식 명칭은 \*\*"이상치 패턴 감지"\*\*다. 회의록의 "이탈 신호 감지"와 DB 설계 문서의 "이상치 패턴"이 갈려 있다. PRD·TRD·SRS가 하나로 통일할 것.

'무기력증', '실행기능 저하' 등 정신건강 진단으로 오해될 표현은 모든 문서에서 사용하지 않는다. **서브 기능 '멘탈 코치'의 사용자 노출 문구에도 동일하게 적용된다.**
