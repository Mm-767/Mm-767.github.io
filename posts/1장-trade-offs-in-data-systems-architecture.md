## 0\. 도입

**장의 목표**

*   데이터 시스템을 평가하고 비교하기 위해 올바른 질문을 하는 방법을 배운다.
    
*   특정 애플리케이션 요구에 가장 적합한 접근 방식을 파악할 수 있다.
    

**애플리케이션 구축 시 준수 사항 — 다섯 가지 기능 요소**

*   데이터를 저장하여 해당 사용자 또는 다른 애플리케이션이 나중에 다시 찾을 수 있도록 한다(**데이터베이스**).
    
*   비용이 많이 드는 작업의 결과를 기억하여 읽기 속도를 높인다(**캐시**).
    
*   사용자가 키워드로 데이터를 검색하거나 다양한 방법으로 필터링할 수 있도록 한다(**검색 인덱스**).
    
*   이벤트와 데이터 변경이 발생하는 즉시 처리한다(**스트림 처리**).
    
*   누적된 대량의 데이터를 주기적으로 처리한다(**배치 처리**).
    

**이 장이 다루는 네 가지 논점**

1.  운영 시스템과 분석 시스템의 차이점
    
2.  클라우드 서비스와 자체 호스팅 시스템의 장단점
    
3.  단일 노드 시스템에서 분산 시스템으로 전환해야 하는 시기
    
4.  비즈니스의 요구사항과 사용자의 권리 사이의 균형

# I. 운영 시스템 대 분석 시스템

## I-1. 두 시스템의 정의

*   **운영 시스템**: 외부 사용자에게 서비스를 제공하는 등 데이터가 생성되는 백엔드 서비스와 인프라. 애플리케이션 코드가 사용자의 행동에 따라 데이터베이스의 데이터를 읽고 수정한다.
    
*   **분석 시스템**: 비즈니스 애널리스트와 데이터 사이언티스트의 요구를 충족한다. 운영 시스템에서 가져온 데이터의 읽기 전용 복사본을 보관하며, 분석에 필요한 데이터 처리 작업에 최적화되어 있다.
    

### 직군의 분리 (누가 데이터를 다루는가?)

*   **분석가 직군 (BA, DS)**: 만들어진 데이터를 분석하여 인사이트를 도출하고 예측 모델을 만든다. (데이터 소비)
    
*   **엔지니어 직군 (DE, AE)**: 분석가들이 데이터를 잘 분석할 수 있도록 양쪽 시스템을 연결하고, 데이터를 정제하는 파이프라인을 구축한다. (데이터 인프라 제공)
    

### 시스템의 분리 (어디서 데이터를 다루는가?)

| 구분 | 운영 시스템 (Operational Systems) | 분석 시스템 (Analytical Systems) |
| --- | --- | --- |
| 주 사용 목적 | 실제 서비스 운영 및 고객 응대 | 비즈니스 의사결정 및 AI/ML 분석 |
| 주요 작업 | 데이터 생성, 읽기, 쓰기, 수정 (Read & Modify) | 원본 데이터의 읽기 전용 복사본 분석 (Read-only) |
| 최적화 방향 | 빠른 트랜잭션 처리와 서비스 안정성 | 대규모 데이터 처리와 복잡한 분석 쿼리 연산 |

데이터 활용을 위해서는 운영(서비스) 영역과 그 데이터를 가져와 인사이트를 뽑는 분석 영역이 나뉘어 있으며, 양쪽 엔지니어 간의 협업이 필수입니다.

## I-2. 트랜잭션

*   상업적 거래(트랜잭션)라는 뜻에서 유래했으며, **하나의 논리적 단위로 묶인 읽기와 쓰기 그룹**을 가리킨다.
    

## I-3. 온라인 트랜잭션 처리(OLTP)

*   운영 시스템은 키를 이용해 적은 수의 레코드를 찾는다(**포인트 쿼리**).
    
*   입력에 따라 레코드를 삽입, 삭제, 업데이트한다.
    
*   사용자와 즉각적으로 상호 작용한다.
    
*   일상적인 서비스 운영 및 실시간 트랜잭션 처리를 담당한다.
    
*   빠르고 잦은 업데이트 → 웹/애플리케이션에서 사용.
    
*   개별 레코드 조회/생성/수정이 중심이다.
    
*   고정되고 미리 정의된 쿼리를 사용한다.
    
*   → 하지만 분석 목적으로 데이터베이스가 사용되면서 **온라인 분석 처리(OLAP)** 가 등장했다.
    

## I-4. 온라인 분석 처리(OLAP)

*   분석 쿼리는 엄청난 수의 레코드를 집계 통계로 계산한다.
    
*   분석 시스템이 담당한다.
    
*   비즈니스 의사결정을 위한 데이터 분석 및 통계가 목적이다.
    
*   비즈니스 분석가(BA), 데이터 사이언티스트, 경영진이 사용한다.
    
*   대량 데이터 집계 및 분석이 중심이다.
    
*   자유롭고 즉흥적인 탐색 쿼리를 사용한다.
    

## I-5. 쿼리 방식의 차이

*   **OLTP (제한적 접근)**: 사용자가 직접 임의의 SQL 쿼리를 작성할 수 없다. 보안상의 문제(접근 권한 없는 데이터 열람)와 성능상의 문제(비효율적인 쿼리로 인한 시스템 마비) 때문이다. 대부분 미리 작성된 고정 쿼리만 실행한다.
    
*   **OLAP (자유로운 접근)**: 데이터 분석가들은 비즈니스 의사결정을 위해 자유롭게 SQL을 작성하거나, Tableau, Looker, Power BI와 같은 대시보드 도구를 통해 데이터를 탐색할 자유가 주어진다.
    

## I-6. 새로운 트렌드: 실시간 분석 시스템

전통적인 OLAP은 데이터 수집이 주로 배치(Batch) 단위로 이루어지지만, 최근에는 이 경계를 허무는 기술들이 등장했습니다.

*   **제품 분석/실시간 분석(Product/Real-time Analytics)**: 분석 작업이긴 하지만, 이를 사용자 대면 서비스(User-facing products) 내부에 직접 내장하는 형태.
    
*   **대표 시스템**: **Pinot, Druid, ClickHouse** 등이 여기에 해당하며, 이들은 데이터를 실시간으로 수집하고 낮은 지연 시간(Low-latency)으로 결과를 응답하도록 최적화되어 있다.
    

## I-7. Data Warehousing

대기업들은 데이터를 분석에 사용하기 시작하면서 OLTP가 적절하지 않다는 것을 알게 됩니다.

**OLTP가 분석에 부적합한 네 가지 이유**

*   관심 있는 데이터가 여러 운영 시스템에 분산될 수 있어, 해당 데이터 세트를 하나의 쿼리로 결합하기가 어려워진다(**데이터 사일로**라고 알려진 문제).
    
*   OLTP에 적합한 스키마와 데이터 레이아웃의 종류는 분석에 덜 적합하다.
    
*   분석 쿼리는 상당히 비용이 많이 들 수 있으며, OLTP 데이터베이스에서 실행하면 다른 사용자의 성능에 영향을 미칠 수 있다.
    
*   OLTP 시스템은 보안 또는 규정 준수상의 이유로 사용자가 직접 접근할 수 없는 별도의 네트워크에 존재할 수 있다.
    

**데이터 웨어하우스(DW)와 ETL/ELT**

*   데이터 웨어하우스에는 회사 내 여러 **OLTP(운영) 시스템**에서 나온 데이터의 **읽기 전용 복사본**이 모인다.
    
*   데이터는 OLTP에서 **추출(Extract)** 되고, 분석에 맞게 **변환(Transform)·정제(Clean)** 된 뒤 웨어하우스에 **적재(Load)** 된다.
    
*   이 전체 과정을 **ETL(Extract–Transform–Load)** 이라 부른다.
    
*   경우에 따라 **적재(Load) 후에 변환(Transform)** 을 수행하기도 하며, 이 흐름은 **ELT(Extract–Load–Transform)** 라고 한다.
    

### HTAP (하이브리드 트랜잭션/분석 처리)

*   일부 데이터베이스 시스템은 하이브리드 트랜잭션/분석 처리(HTAP)를 제공한다.
    
*   ETL 없이 단일 시스템에서 OLTP와 분석을 모두 가능하게 하는 것이 목적이다.
    
*   많은 HTAP 시스템은 내부적으로 OLTP 시스템과 별도의 분석 시스템으로 구성되어 있으며, 공통 인터페이스 뒤에 숨겨져 있다.
    
*   → 따라서 두 시스템을 구분하는 것이 이러한 시스템이 어떻게 작동하는지 이해하는 데 여전히 중요하다.
    
*   그렇다고 해서 데이터 웨어하우스를 대체하지는 않는다.
    

## I-8. From Data Warehouse to Data Lake

**주제**: Operational Systems 대비 Analytical Systems — Data Warehouse에서 Data Lake로의 전환

### (1) Data Warehouse의 한계와 Data Science의 요구사항

*   **기존 시스템의 한계**: Relational Data Model과 SQL 기반의 Data Warehouse는 Business Analyst(BI)에게는 유용하나, Data Scientist의 고도화된 작업에는 부적합하다.
    
*   **Feature Engineering의 어려움**: Machine Learning(ML) 모델 훈련을 위해서는 데이터베이스의 행과 열을 숫자 **Vector**나 **Matrix** 형태(**Features**)로 변환해야 한다. 이는 성능 극대화에 필수적이나, SQL만으로는 구현하기 힘든 **Custom Code**가 필요하다.
    
*   **비정형 데이터 처리 불가**: 리뷰와 같은 텍스트 데이터에서 감정이나 주제를 추출하는 Natural Language Processing(NLP)나, 사진에서 정보를 추출하는 Computer Vision 작업을 Relational Database에서 수행하기는 어렵다.
    

### (2) Data Scientist의 선호 분석 환경

*   **Relational Database 기피**: Relational Data Model 위에 ML 시스템을 구축하려는 시도가 있었으나, 실무자들은 이를 선호하지 않는다.
    
*   **선호하는 도구**: Data Scientist들은 Schema에 얽매이지 않는 유연한 도구를 주로 사용한다.
    
*   **주요 활용 기술**: Python Data Analysis Library(Pandas, scikit-learn), Statistical Analysis Language(R), Distributed Analytics Framework(Spark) 등.
    

### (3) 새로운 대안: Data Lake의 정의와 특징

*   **핵심 정의**: Operational Systems에서 생성된 분석용 데이터를 복사해 모아두는 '**Centralized Data Repository**'이다.
    
*   **무제한적 유연성**: Data Warehouse와 달리 특정 File Format, Data Model, Schema를 사전에 강제하지 않는다.
    
*   **다양한 Data Format 수용**: Avro나 Parquet 같은 정형화된 Database Records뿐만 아니라 텍스트, 이미지, 비디오, 센서 판독값, 유전체 시퀀스 등 모든 형태의 데이터를 저장할 수 있다.
    
*   **비용 절감**: Cloud Native Architecture의 Object Stores 등 범용 파일 스토리지를 활용하므로 기존 Relational Storage보다 구축 및 유지 비용이 저렴하다.
    

### (4) Data Pipelines의 진화와 'Sushi Principle'

*   **Pipeline의 중간 기착지**: 기존의 ETL 프로세스는 'Data Pipelines'로 진화했으며, Data Lake는 Operational Systems에서 Data Warehouse로 넘어가는 중간 저장소 역할을 수행하기도 한다.
    
*   **Sushi Principle**: "**Raw Data가 더 낫다**"는 핵심 철학이다. 데이터를 특정 Schema로 미리 변형하지 않고 날것 그대로 보관한다.
    
*   **Data Consumer의 자율성 극대화**: Raw Data를 그대로 보관함으로써, 데이터를 활용하는 각 사용자가 자신의 목적과 필요에 가장 잘 맞는 형태로 직접 데이터를 가공하고 변환(Transform)하여 사용할 수 있다.
    

> 원문에는 이어서 _Beyond the data lake_ 소제목이 존재하나, 노트에 본문 내용은 채워져 있지 않습니다.

## I-9. Systems of Record and Derived Data

### (1) 기록 시스템 (Systems of Record)

**핵심 개념**: 데이터의 유일한 진실 공급원(Source of Truth)이자 권위 있는 표준 시스템이다.

*   **데이터의 첫 도착지**: 사용자 입력 등 새로운 데이터가 시스템에 유입될 때 가장 먼저 기록되는 곳이다.
    
*   **정규화와 단일성**: 데이터의 각 사실(Fact)은 중복 없이 정확히 한 번만 표현되며, 일반적으로 데이터가 정규화(Normalized)되어 있다.
    
*   **절대적 기준**: 다른 시스템과 데이터 불일치가 발생할 경우, 항상 기록 시스템의 값이 정답으로 간주된다.
    

### (2) 파생 데이터 시스템 (Derived Data Systems)

**핵심 개념**: 기존 데이터를 가져와 변환, 가공, 처리하여 생성된 데이터를 보관하는 시스템이다.

*   **재생성 가능성**: 데이터가 손실되더라도 원본 기록 시스템에서 다시 생성(복구)할 수 있다.
    
*   **목적과 성능**: 기술적으로는 중복된 데이터지만, 시스템의 **읽기 쿼리 성능을 대폭 향상**시키는 데 필수적인 역할을 한다. 단일 소스에서 여러 관점의 데이터세트를 도출할 수 있다.
    
*   **주요 사례**: 캐시(Cache), 비정규화된 데이터, 인덱스(Indexes), 구체화된 뷰(Materialized views), 변환된 데이터 표현, 데이터세트로 학습된 모델 등.
    

### (3) 아키텍처 내 시스템별 적용 및 도구의 유연성

**핵심 개념**: 데이터베이스 도구 자체의 특성보다는 '애플리케이션이 데이터를 어떻게 사용하는가'가 시스템의 성격을 결정한다.

*   **분석 시스템**: 다른 곳에서 생성된 데이터를 소비하므로 대부분 파생 데이터 시스템으로 작동한다.
    
*   **운영 서비스**: 두 시스템이 혼합되어 사용된다. 쓰기 작업은 '기록 시스템'인 기본 DB에, 빠른 읽기 작업은 '파생 시스템'인 인덱스나 캐시에 할당하는 방식이다.
    
*   **아키텍처의 명확성**: 데이터베이스나 스토리지 엔진은 단순한 '도구'일 뿐이다. 어떤 데이터가 어느 원본에서 파생되었는지 관계를 명확히 정의하면 복잡한 시스템 아키텍처를 쉽게 이해하고 설계할 수 있다.
    

### (4) 데이터 통합 및 동기화 과제

**핵심 개념**: 분리된 시스템 간의 데이터 일관성을 유지하기 위한 업데이트 프로세스가 필요하다.

*   **업데이트 전파**: 기록 시스템의 원본이 변경되면 파생 데이터 시스템의 데이터도 반드시 업데이트되어야 한다.
    
*   **기존 DB의 한계**: 많은 데이터베이스가 단일 DB 사용을 가정하고 설계되어, 여러 시스템 간의 업데이트를 통합하고 전파하는 기능이 부족하다.
    
*   **해결 방향(데이터 파이프라인)**: 단일 시스템이 할 수 없는 작업을 수행하고 여러 시스템을 통합하기 위해 **데이터 파이프라인(Data pipelines)** 아키텍처가 도입된다(11장에서 상세히 다룸).

# II. Cloud Versus Self-Hosting

## II-1. 소프트웨어 구축 및 배포 전략: 자체 개발 vs 구매 (Build vs. Buy)

### (1) 의사결정의 핵심 기준: 비즈니스 우선순위

**핵심 개념**: 기능을 자체적으로 해결할지 외주(아웃소싱)를 줄 것인지는 궁극적으로 비즈니스 우선순위에 달려 있다.

*   **자체 개발(In-house)**: 조직의 핵심 역량(Core competency)이거나 경쟁 우위(Competitive advantage)를 가져다주는 영역에 집중해야 한다.
    
*   **외주/구매(Outsource/Buy)**: 비핵심적이거나, 일상적이고 보편적인 기능은 외부 벤더에 맡기는 것이 원칙이다.
    
*   **사례**: 극단적인 예로, 대부분의 기업은 비용 효율성을 위해 CPU를 직접 설계·제작하지 않고 반도체 제조사에서 구매한다.
    

### (2) 소프트웨어 아키텍처 스펙트럼

**핵심 개념**: 소프트웨어 전략은 '누가 소프트웨어를 구축하는가'와 '누가 배포 및 운영하는가'라는 두 가지 결정에 따라 스펙트럼이 나뉜다.

*   **1단계: 자체 개발 & 자체 운영(In-house software, in-house operations)** — 조직이 직접 코드를 작성하고 내부에서 실행하는 맞춤형(Bespoke) 소프트웨어다. 시스템에 대한 **통제력이 가장 높지만**, 그만큼 막대한 **투자 비용**이 요구된다.
    
*   **2단계: 기성품 소프트웨어 & 자체 운영(Off-the-shelf software, in-house operations)** — 오픈소스나 상용 기성품을 가져와 직접 제어하는 서버(온프레미스 하드웨어 또는 클라우드의 IaaS 가상 머신)에 설치 및 호스팅하는 방식이다(예: MySQL 다운로드 및 직접 운영).
    
*   **3단계: 기성품 소프트웨어 & 외주 운영(Off-the-shelf software, outsourced operations)** — 외부 벤더가 완벽히 구현하고 운영하며, 사용자는 웹 인터페이스나 API를 통해서만 접근하는 클라우드 서비스 또는 SaaS 제품이다. 시스템에 대한 **통제력은 낮지만**, 필요한 **투자 비용도 가장 적다**.
    

### (3) 배포 환경과 도구의 한계성 (참고)

*   **배포 방식**: 서비스를 클라우드와 온프레미스 중 어디에 둘 것인지, 쿠버네티스(Kubernetes)와 같은 오케스트레이션 프레임워크를 사용할 것인지 등의 문제도 연관되어 있다.
    
*   **논의 범위 제외**: 이러한 배포 도구의 선택은 인프라 구성에 중요하지만, 데이터 시스템 자체의 근본적인 아키텍처에 미치는 영향력은 상대적으로 적으므로 해당 서적의 핵심 논의 대상에서는 제외된다.
    

## II-2. Pros and Cons of Cloud Services

클라우드 서비스를 사용하는 것은 본질적으로 소프트웨어의 '운영'을 클라우드 제공업체에 아웃소싱하는 것이다. 두 방식은 조직의 역량, 작업 부하의 특성, 그리고 통제권의 필요성에 따라 극명한 장단점을 가진다.

### (1) 비용 및 운영 효율성 비교

**핵심 개념**: 인프라 관리 역량과 트래픽의 예측 가능성이 선택의 기준이 된다.

*   **자체 호스팅이 유리한 경우**: 시스템 운영 경험이 풍부하고, 트래픽 부하가 예측 가능(Predictable)할 때 일반적으로 더 저렴하다. 또한 특정 작업 부하에 맞춰 시스템을 세밀하게 튜닝하고 구성해야 할 때 필수적이다.
    
*   **클라우드가 유리한 경우**: 시스템 운영 지식이 부족하거나 빠른 배포가 필요할 때 적합하다. 인프라 전담 인력 채용 및 교육 비용을 아낄 수 있으며, 내부 팀이 더 가치 있는 상위 수준의 업무에 집중할 수 있도록 돕는다.
    

### (2) 작업 부하(Workload)와 확장성

**핵심 개념**: 리소스 사용량이 가변적인 환경에서는 클라우드가 절대적인 비용 우위를 가진다.

*   **유휴 자원 최소화**: 피크 타임에 맞춰 자체 머신을 구축하면 평소에는 자원이 낭비(Idle)된다. 클라우드는 수요 변화에 따라 컴퓨팅 리소스를 쉽게 확장/축소(Scale up/down)할 수 있어 경제적이다.
    
*   **분석 시스템 사례**: 대규모 분석 쿼리는 실행 시 막대한 병렬 컴퓨팅 자원을 소모하지만, 완료 후에는 유휴 상태가 된다. 클라우드를 사용하면 작업 후 잉여 자원을 즉시 반환하여 비용을 절감할 수 있다(데이터 세트가 클수록 효과가 큼).
    

### (3) 클라우드 서비스의 주요 단점: 통제권 상실

**핵심 개념**: 운영을 외부에 맡김으로써 발생하는 시스템 및 데이터에 대한 '제어력 부족'이 가장 큰 리스크다.

*   **기능 및 장애 의존성**: 필요한 기능이 없거나 서비스가 다운되었을 때 직접 해결할 수 없으며, 벤더의 조치만을 기다려야 한다.
    
*   **디버깅의 한계**: OS 성능 지표나 서버 내부 로그에 접근할 수 없어 버그나 성능 저하의 원인을 진단하기 매우 어렵다.
    
*   **벤더 종속성(Lock-in)**: 서비스 종료, 가격 인상, 원치 않는 제품 변경 시 구버전을 유지할 수 없어 강제 마이그레이션이 발생한다. 표준 API가 없는 경우 타 서비스로 전환하는 비용이 매우 높다.
    
*   **지정학적 리스크**: 국가 간 정치적 갈등이나 제재로 인해 서비스 접근 자체가 차단될 위험이 있다.
    
*   **보안 및 규제**: 데이터를 외부 공급업체에 위탁하므로 개인정보 보호 및 보안 규정 준수가 더 복잡해진다.
    

### (4) 결론 및 하이브리드 접근법

*   **현대적 흐름**: 수많은 리스크에도 불구하고, 클라우드 위에 신규 애플리케이션을 구축하거나 시스템 일부만 클라우드를 사용하는 **하이브리드(Hybrid)** 방식이 대세로 자리 잡고 있다.
    
*   **자체 호스팅의 지속성**: 초고주파 매매(HFT)와 같이 극도로 낮은 지연 시간(Latency)과 하드웨어에 대한 완전한 통제권이 필요한 특수 시스템이나, 클라우드 이전의 레거시 시스템에서는 여전히 자체 호스팅이 필수적이다.
    

## II-3. Cloud Native System Architecture

클라우드의 부상은 단순한 경제 모델의 변화를 넘어 데이터 시스템이 구현되는 기술적 방식에 근본적인 영향을 미쳤다. 이를 설명하는 핵심 개념이 '클라우드 네이티브(Cloud Native)'이다.

### (1) 경제적 모델의 패러다임 전환

**핵심 개념**: 자산 소유에서 서비스 구독으로의 전환이다.

*   기존의 하드웨어 구매 및 소프트웨어 라이선스 취득 방식에서 벗어나, 필요한 만큼 사용하는 **서비스 구독(Subscription)** 모델로 변화했다.
    

### (2) 클라우드 네이티브 아키텍처의 정의

**핵심 개념**: 처음부터 클라우드 서비스의 이점을 극대화하도록 설계된 시스템 아키텍처를 의미한다.

*   기존의 자체 호스팅이 가능한 소프트웨어도 클라우드에서 '관리형 서비스(Managed Service)'로 제공될 수는 있으나, 태생부터 클라우드를 위해 구축된 시스템과는 확연한 차이가 존재한다.
    

### (3) 클라우드 네이티브 시스템의 핵심 이점

기존 시스템을 클라우드로 단순히 이식한 것과 비교하여 다음의 이점을 제공한다.

*   **성능 최적화**: 동일한 하드웨어 인프라 조건에서도 더 나은 성능을 발휘한다.
    
*   **회복 탄력성**: 장애(Failures) 발생 시 훨씬 더 빠른 복구가 가능하다.
    
*   **신속한 확장성**: 작업 부하(Load)의 변화에 맞춰 컴퓨팅 리소스를 즉각적이고 빠르게 확장(Scale)할 수 있다.
    
*   **대규모 데이터 처리**: 훨씬 더 큰 규모의 데이터세트를 안정적으로 지원하고 처리할 수 있다.

## II-4. Layering of Cloud Services

### (1) 자체 호스팅 데이터 시스템의 특징

*   **단순한 요구 사항**: 일반적인 운영 체제(Linux, Windows)에서 실행되며, 데이터를 파일 시스템에 저장하고 TCP/IP 등 표준 네트워크 프로토콜을 통해 통신한다.
    
*   **범용 리소스 의존**: 머신러닝을 위한 GPU나 RDMA 같은 특수 하드웨어가 필요한 경우도 일부 있으나, 대부분 CPU, RAM, 파일 시스템, IP 네트워크와 같은 범용 컴퓨팅 리소스를 사용한다.
    

### (2) 클라우드 IaaS(서비스형 인프라) 환경

*   **VM(가상 머신) 활용**: 자체 호스팅 소프트웨어는 클라우드의 IaaS 환경에서 특정 리소스(CPU, 메모리, 디스크, 대역폭)가 할당된 인스턴스를 통해 실행될 수 있다.
    
*   **물리적 머신과의 차이**: 물리적 장비보다 프로비저닝(준비 및 배포) 속도가 빠르고 크기 선택의 폭이 넓다.
    
*   **관리 책임**: 자유롭게 소프트웨어를 실행할 수 있지만, 직접 관리하고 운영해야 한다는 점에서는 전통적인 컴퓨터와 유사하다.
    

### (3) 클라우드 네이티브 서비스의 핵심: 계층화(Layering)

*   **핵심 개념**: 단순히 OS가 관리하는 컴퓨팅 리소스를 사용하는 것을 넘어, **하위 수준의 클라우드 서비스를 기반으로 상위 수준의 서비스를 구축**하는 것이다.
    
*   **계층화 사례 1 — 객체 스토리지(Amazon S3, Azure Blob Storage 등)**
    
    *   일반 파일 시스템보다 API는 제한적(기본적인 읽기/쓰기)이지만 대용량 파일 저장에 최적화되어 있다.
        
    *   물리적 머신을 추상화하여 사용자에게 숨긴다.
        
    *   데이터를 여러 머신에 자동 분산시켜 단일 머신의 용량 부족 문제를 해결하고, 하드웨어 장애 시에도 데이터 손실을 방지한다.
        
*   **계층화 사례 2 — 상위 서비스 구축(Snowflake 등)**
    
    *   클라우드 기반 분석 데이터베이스(데이터 웨어하우스)인 Snowflake는 하위 계층인 S3(객체 스토리지)를 데이터 저장소로 의존하여 구축된다.
        
    *   또 다른 고차원 서비스들은 이 Snowflake를 기반으로 다시 계층을 쌓아 구축된다.
        

### (4) 시스템 추상화 수준 선택 가이드

*   컴퓨팅 추상화 선택에 있어 절대적인 정답은 없다.
    
*   **상위 수준 시스템 선택**: 특정 사용 사례에 맞춰 설계되어 있다. 요구 사항이 시스템의 목적과 일치한다면, 하위 구성 요소로 직접 구축하는 것보다 훨씬 편리하고 효율적이다.
    
*   **하위 수준 시스템 선택**: 현재 요구 사항을 충족하는 상위 수준 시스템이 존재하지 않을 경우, 하위 수준의 컴포넌트를 결합해 직접 시스템을 구축하는 것이 유일한 대안이다.
    

## II-5. Separation of Storage and Compute

**분석 주제**: 전통적 스토리지와 클라우드 네이티브 스토리지의 구조적 차이 및 특징

### (1) 전통적 컴퓨팅의 디스크 스토리지

*   **영구적 보존**: 데이터가 디스크에 기록되면 유실되지 않는 영구적인 저장소로 간주된다.
    
*   **RAID 활용**: 개별 하드 디스크 장애를 극복하기 위해 데이터를 여러 디스크에 복제하는 RAID(독립 디스크의 중복 배열)가 주로 사용된다.
    
*   **투명성**: RAID는 하드웨어 또는 OS 수준에서 구현되며, 파일 시스템에 접근하는 애플리케이션에는 투명하게(transparent) 작동한다.
    

### (2) 클라우드 인스턴스(VM)의 로컬 디스크

*   **휘발성 캐시 역할**: 클라우드 네이티브 시스템에서는 로컬 디스크를 장기 저장소가 아닌 임시 캐시처럼 취급한다.
    
*   **데이터 접근 불가 위험**: 인스턴스 장애가 발생하거나, 부하 조절을 위해 다른 물리적 머신의 인스턴스로 교체될 경우 해당 로컬 디스크의 데이터에 접근할 수 없기 때문이다.
    

### (3) 가상 디스크 스토리지 (Virtual Disk Storage)

*   **유연한 연결**: Amazon EBS, Azure Managed Disks 등과 같이 한 인스턴스에서 분리해 다른 인스턴스에 연결할 수 있는 클라우드 서비스이다.
    
*   **블록 디바이스 에뮬레이션**: 물리적 디스크가 아닌 여러 머신이 디스크(보통 4KiB 블록)의 동작을 모방하는 방식이다. 전통적인 디스크 기반 소프트웨어를 클라우드에서 실행할 수 있게 해준다.
    
*   **구조적 단점**: 에뮬레이션으로 인한 오버헤드가 존재하며, 모든 I/O 작업이 네트워크 호출을 통해 이루어지므로 네트워크 오류에 매우 민감하다.
    

### (4) 클라우드 네이티브 및 객체 스토리지 (Object Storage)

*   **전용 스토리지 최적화**: 가상 디스크의 한계를 피하기 위해 워크로드에 맞춰 최적화된 스토리지 서비스(예: Amazon S3)를 사용한다.
    
*   **역할 분담**: 객체 스토리지는 대용량 파일의 장기 보관에 적합하다. 따라서 클라우드 데이터베이스는 작은 데이터 값은 별도의 서비스로 관리하고, 대용량 데이터 블록만 객체 저장소에 보관하는 방식을 취한다.
    

### (5) 컴퓨팅과 스토리지의 분리 (Disaggregation)

*   **아키텍처 변화**: 스토리지(디스크)와 연산(CPU, RAM)을 동일한 컴퓨터가 처리하던 전통적 방식과 달리, 클라우드 네이티브 시스템은 이 두 역할을 물리적·논리적으로 분리한다.
    
*   **네트워크 의존성 증가**: 저장소(S3 등)와 분석 코드 실행 환경이 분리되어 있으므로, 데이터 처리를 위해서는 네트워크를 통한 데이터 전송이 필수적이다.
    

### (6) 멀티테넌시 (Multitenancy)

*   **자원 공유**: 고객마다 개별 장비를 할당하지 않고, 동일한 공유 하드웨어와 서비스에서 여러 고객의 데이터와 연산을 동시에 처리한다.
    
*   **장점**: 하드웨어 활용도 극대화, 쉬운 확장성, 클라우드 제공자의 관리 효율성을 보장한다.
    
*   **단점**: 한 고객의 작업이 다른 고객의 시스템 성능이나 보안에 악영향을 미치지 않도록 철저한 격리(Isolation) 엔지니어링이 요구된다.
    

## II-6. Operations in the Cloud Era

*   **운영 역할의 진화**: 전통적으로 분리되어 있던 역할(DBA, 시스템 관리자)이 백엔드 서비스와 데이터 인프라를 공동으로 책임지는 DevOps 및 SRE(사이트 신뢰성 엔지니어링) 모델로 통합되는 추세입니다.
    
*   **인프라 패러다임의 변화**
    
    *   **자체 호스팅 시스템**: 디스크 공간 모니터링, 신규 하드웨어 프로비저닝, OS 패치 등 개별 머신 수준의 수동 작업과 선제적인 용량 계획이 필수적이다.
        
    *   **클라우드 서비스**: API를 통해 물리적 하드웨어를 추상화한다. 사전 용량 계획 대신 사용량 기반(Metered billing) 청구 방식을 사용하며, 개별 머신의 장애가 발생하더라도 높은 가용성을 유지한다.
        
*   **DevOps/SRE 핵심 지침 및 철학**
    
    *   수동 일회성 작업보다 반복 가능한 프로세스를 선호하여 **자동화 구축**
        
    *   장기간 실행되는 고정 서버 대신 **임시(Ephemeral) VM 및 서비스 활용**
        
    *   애플리케이션의 **빈번한 업데이트 지원 및 활성화**
        
    *   시스템 장애 및 인시던트(Incidents)로부터의 **지속적인 학습**
        
    *   인력 변동과 무관하게 시스템에 대한 **조직적 지식 보존**
        
*   **운영 역할의 양분화**: 클라우드 인프라 제공업체의 운영팀은 대규모 고객을 위한 서비스 신뢰성 확보에 전념하는 반면, 서비스 고객은 인프라 관리에 드는 시간과 노력을 최소화하는 방향으로 역할이 분리되었습니다.
    
*   **클라우드 고객의 필수 유지 운영 책임** — 인프라 관리가 줄어들었음에도 다음 영역에 집중해야 합니다.
    
    *   **비용 최적화**: 전통적인 '용량 계획'은 '재무 계획'으로, '성능 최적화'는 '비용 최적화'로 전환된다. 불필요한 리소스에 비용이 낭비되지 않도록 관리해야 한다.
        
    *   **할당량(Quota) 및 제한 관리**: 벤더가 설정한 리소스 제한(예: 동시 실행 프로세스의 최대 수)을 초과하기 전에 미리 파악하고 대응 계획을 세워야 한다.
        
    *   **서비스 통합**: 클라우드 서비스 간의 통합을 촉진할 표준이 아직 부족하므로, 다양한 공급업체의 서비스를 연결하고 통합하는 데 여전히 상당한 수동 노력이 필요하다.
        
    *   **보안 및 트러블슈팅**: 애플리케이션 및 종속 라이브러리의 보안 유지, 부하 모니터링, 자체 서비스 간의 상호작용 관리, 성능 저하 및 장애 원인 추적은 클라우드에 온전히 위임할 수 없는 핵심 책임이다.

# III. 분산 시스템 vs 단일 노드 시스템

**핵심 정의**: 네트워크를 통해 여러 대의 머신이 통신하는 시스템을 **분산 시스템**이라 하고, 여기에 참여하는 각 프로세스를 **노드**라고 합니다.

## III-1. 분산 시스템을 채택하는 9가지 이유

| 이유 | 내용 |
| --- | --- |
| 본질적 분산성 | 사용자가 각자 자기 기기를 쓰며 상호작용하는 앱은 애초에 네트워크 통신이 불가피함 |
| 클라우드 서비스 간 요청 | 저장 서비스와 처리 서비스가 분리되면 데이터가 네트워크를 오감. 클라우드 네이티브·마이크로서비스가 본질적으로 분산인 이유 |
| 내결함성/고가용성 | 머신·네트워크·데이터센터 하나가 죽어도 다른 쪽이 넘겨받도록 이중화 |
| 확장성 | 데이터량이나 연산량이 단일 머신 한계를 넘으면 여러 머신에 부하 분산 |
| 지연 시간 | 전 세계 사용자에게 지리적으로 가까운 서버에서 응답해 패킷 왕복 시간을 줄임 |
| 탄력성 | 바쁠 때 늘리고 한가할 때 줄여 실제 쓴 만큼만 지불. 단일 머신은 최대 부하 기준으로 미리 갖춰야 해서 비효율 |
| 특화 하드웨어 | 워크로드별 최적 하드웨어 사용 — 오브젝트 스토리지는 디스크 多·CPU 少, 데이터 분석은 CPU/메모리 多·디스크 無, ML은 GPU(딥러닝 학습에서 CPU보다 훨씬 효율적) |
| 법적 준수 | 데이터 레지던시 법규상 자국민 데이터를 자국 내에서 저장·처리해야 하는 경우(의료·금융에 한정되기도, 더 광범위하기도). 여러 관할권에 사용자가 있으면 데이터 분산 불가피 |
| 지속가능성 | 재생에너지가 풍부한 시간·장소에서 작업을 돌리고 전력망 부하가 큰 시점은 피해 탄소 배출과 전력 비용 절감 |

**마무리**: 이 이유들은 직접 작성한 애플리케이션 코드뿐 아니라 데이터베이스 같은 기성 소프트웨어로 구성된 서비스에도 똑같이 적용됩니다.

## III-2. Problems with Distributed Systems

**출처 위치**: Chapter 1, p.20 / 직전 섹션 "Distributed Versus Single-Node Systems"에 이어지는 후반부

### 섹션 구조 개요

**한 줄 요지**: 분산 시스템은 실패·지연·진단난이도·일관성 부담이라는 비용을 수반하며, 하드웨어 발전으로 이제 상당수 워크로드는 단일 노드가 더 단순하고 저렴한 답이다.

### (1) 네트워크 실패와 불확실성

*   네트워크를 넘나드는 **모든 요청과 API 호출**은 실패 가능성을 전제로 설계해야 함
    
*   실패 유형: 네트워크 중단 / 서비스 과부하 / 서비스 크래시 → 결과적으로 **응답 없는 타임아웃**
    
*   핵심 난점: 타임아웃 시 **서비스가 요청을 수신했는지 여부를 알 수 없음**
    
*   따라서 **단순 재시도가 안전하지 않을 수 있음**(중복 실행 위험)
    
*   → Chapter 9에서 상세 논의
    

### (2) 성능에 대한 오해

*   **네트워크 호출 비용**: 데이터센터 네트워크가 빠르다는 전제에도 불구하고, **타 서비스 호출은 동일 프로세스 내 함수 호출보다 압도적으로 느림** `[43]`
    
*   **데이터 이동 vs 연산 이동**: 대용량 데이터 처리 시, 스토리지 → 별도 처리 머신으로 데이터를 옮기는 것보다 **연산을 데이터가 이미 있는 머신으로 가져가는 편이 더 빠를 수 있음** `[44]`
    
*   **노드 수 ≠ 속도**: 노드를 늘린다고 항상 빨라지지 않음. 반례로 **컴퓨터 1대의 단순 단일 스레드 프로그램**이 **CPU 코어 100개 초과 클러스터**보다 유의미하게 나은 성능을 낸 사례가 있음 `[45]`
    

### (3) 트러블슈팅의 어려움

*   문제 상황: 시스템 응답이 느릴 때 **원인 지점을 특정하기 어려움**
    
*   대응 분야: **관측 가능성(observability)** `[46, 47]`
    
*   관측 가능성의 정의 — 다음 두 가지를 포함
    
    1.  시스템 실행에 관한 데이터를 수집
        
    2.  그 데이터를 **고수준 지표(metrics)** 와 **개별 이벤트** 양쪽 모두로 분석 가능하도록 질의
        
*   **추적(tracing) 도구**: OpenTelemetry, Zipkin, Jaeger `[48]`. 추적 가능 항목은 ① 어떤 클라이언트가 ② 어떤 서버에 ③ 어떤 연산을 호출했는지 ④ 각 호출이 얼마나 걸렸는지.
    

### (4) 서비스 간 데이터 일관성

*   데이터베이스는 자체적으로 다양한 일관성 보장 메커니즘을 제공(→ Ch.6, Ch.8)
    
*   그러나 **서비스마다 자체 DB를 보유**하면, 서비스 간 데이터 일관성 유지는 **애플리케이션의 책임**으로 넘어감
    
*   해법 후보: **분산 트랜잭션(distributed transactions)** (→ Ch.8)
    
*   분산 트랜잭션이 마이크로서비스에서 거의 쓰이지 않는 이유 두 가지 `[49]`: **서비스 간 독립성 확보라는 목표에 역행**, **많은 DB가 지원하지 않음**
    

### (5) 결론 — 단일 노드의 재부상

*   위 모든 이유로, **단일 머신에서 작업을 수행하는 편이 분산 시스템 구축보다 훨씬 단순하고 저렴한 경우가 많음** `[22, 45, 50]`
    
*   하드웨어 추세: CPU·메모리·디스크가 지속적으로 **더 커지고, 더 빨라지고, 더 안정적으로** 발전
    
*   여기에 **단일 노드 데이터베이스**를 결합하면 다수 워크로드가 노드 1대로 처리 가능 — 예시: **DuckDB, SQLite, KuzuDB**
    
*   → Chapter 4에서 심화 탐구
    

### (6) 종합 정리

*   **앞 섹션과의 대비 구조**: 직전 섹션이 분산을 택하는 9가지 이유(본질적 분산성·확장성·내결함성 등)를 나열했다면, 이 섹션은 그 반대편 비용을 제시해 **트레이드오프 판단의 균형점**을 세웁니다. 챕터 제목이 "Trade-Offs"인 이유가 여기서 드러납니다.
    
*   **저자의 실무적 입장**: 분산을 기본값으로 두지 말 것. 분산은 명확한 필요(앞 섹션의 9가지 중 실제 해당 사항)가 있을 때 지불하는 비용이며, 그렇지 않다면 단일 노드가 우선 검토 대상입니다.
    
*   **챕터 로드맵**: Ch.4 → 단일 노드 vs 분산 데이터 시스템, Ch.6 → 복제와 일관성, Ch.8 → 트랜잭션·분산 트랜잭션, Ch.9 → 분산 시스템의 실패 모델

### ① 클라이언트-서버: 분산의 기본형

*   시스템을 여러 머신에 분산하는 **가장 흔한 방식**은 클라이언트와 서버로 나누고, 클라이언트가 서버에 요청을 보내는 것입니다.
    
*   통신 프로토콜로는 **HTTP가 가장 일반적**이며, 상세 논의는 "Dataflow Through Services: REST and RPC"(p.180)로 연결됩니다.
    
*   **하나의 프로세스가 서버와 클라이언트 역할을 동시에** 수행할 수 있습니다. 들어오는 요청을 처리하면서, 다른 서비스로 나가는 요청을 만드는 경우입니다.
    

### ② SOA에서 마이크로서비스로

*   이 방식은 전통적으로 **서비스 지향 아키텍처(SOA)** 로 불렸고, 최근 **마이크로서비스 아키텍처**로 정련되었습니다 `[51, 52]`.
    
*   마이크로서비스의 세 가지 정의 요건: 서비스는 **하나의 잘 정의된 목적**을 가지고(예: S3의 경우 파일 저장), **네트워크를 통해 클라이언트가 호출할 수 있는 API를 노출**하며, **유지관리를 책임지는 하나의 팀**을 갖습니다.
    
*   복잡한 애플리케이션은 상호작용하는 여러 서비스로 분해되고, 각 서비스는 별도 팀이 관리합니다.
    
*   **클라우드 네이티브 시스템이 서비스 분해를 많이 사용**하지만, 온프레미스 시스템도 서비스 지향 접근을 채택할 수 있습니다.
    

### ③ 서비스 분할의 이점

*   **독립 배포**: 각 서비스를 독립적으로 업데이트할 수 있어 팀 간 조율 비용이 줄어듭니다.
    
*   **자원 개별 할당**: 각 서비스에 필요한 만큼의 하드웨어 자원을 배정할 수 있습니다.
    
*   **구현 은닉**: API 뒤에 구현 세부를 감추므로, 서비스 소유자는 클라이언트에 영향을 주지 않고 구현을 바꿀 수 있습니다.
    
*   **데이터 저장 원칙 — 서비스별 독립 DB**: 각 서비스가 자기 데이터베이스를 갖고 **서비스 간 DB를 공유하지 않는 것이 일반적**입니다. 이유는 두 가지로, DB를 공유하면 **데이터베이스 구조 전체가 사실상 그 서비스 API의 일부가 되어** 구조 변경이 어려워지고, 공유 DB에서는 **한 서비스의 쿼리가 다른 서비스의 성능을 악화**시킬 수 있습니다.
    

### ④ 서비스 분할의 비용과 난점

*   서비스가 많아지는 것 자체가 **복잡성을 낳습니다**.
    
*   **개발 중 테스트가 까다로워집니다**. 해당 서비스가 의존하는 다른 모든 서비스도 함께 실행해야 하기 때문입니다.
    
*   각 서비스마다 다음 인프라가 필요합니다: **신규 릴리스 배포, 부하에 맞춘 하드웨어 자원 조정, 로그 수집, 서비스 헬스 모니터링, 문제 발생 시 온콜 엔지니어 알림**.
    
*   **Kubernetes 같은 오케스트레이션 프레임워크**가 이 인프라의 기반을 제공하기 때문에 서비스 배포 방식으로 널리 쓰이게 되었습니다.
    
*   **API 진화(evolution)의 어려움**: 클라이언트는 API에 특정 필드가 있으리라 기대하는데, 비즈니스 요구 변화로 필드를 추가·삭제하면 클라이언트가 실패할 수 있습니다.
    
*   더 나쁜 점은, 이런 실패가 **개발 주기 후반, 즉 갱신된 API가 스테이징이나 프로덕션에 배포된 뒤에야 발견되는 경우가 많다**는 것입니다.
    
*   완화 수단: **OpenAPI, gRPC** 같은 API 기술(description) 표준이 클라이언트-서버 API 관계 관리를 돕습니다(상세는 Chapter 5).
    

### ⑤ 도입 판단 기준 — 이 절의 핵심 명제

*   **마이크로서비스는 본질적으로 사람 문제에 대한 기술적 해법**입니다. 서로 조율하지 않고도 여러 팀이 독립적으로 진척을 낼 수 있게 하는 것이 목적입니다.
    
*   따라서 **대기업에서는 가치가 있지만**, 팀 수가 적은 **소규모 회사에서는 불필요한 오버헤드**가 될 가능성이 높고, **가능한 가장 단순한 방식으로 구현하는 편이 낫습니다** `[51]`.
    

### ⑥ 서버리스 / FaaS

*   **서버리스(= function as a service, FaaS)** 는 서비스 배포의 또 다른 접근으로, **인프라 관리를 클라우드 벤더에 위탁**하는 방식입니다 `[32]`.
    
*   **VM과의 대비**: VM은 인스턴스를 언제 켜고 끌지 사용자가 명시적으로 선택해야 하지만, 서버리스는 **들어오는 요청에 따라 클라우드 제공자가 하드웨어 자원을 자동으로 할당·해제**합니다 `[53]`.
    
*   **과금 모델의 유비**: 클라우드 스토리지가 용량 계획(디스크를 몇 개 살지 미리 결정)을 계량 과금으로 대체했듯, 서버리스는 **코드 실행에 계량 과금을 도입**합니다. 자원을 미리 프로비저닝하는 대신 **애플리케이션 코드가 실행된 시간만큼만 지불**합니다.
    
*   **제약 세 가지**: 그 이점을 제공하기 위해 많은 제공자가 **함수 실행 시간 제한**을 두고, **런타임 환경을 제한**하며, 함수가 **처음 호출될 때 느린 시작(slow start)** 이 발생할 수 있습니다.
    
*   **용어의 오해 소지**: "서버리스"라는 말은 오해를 부를 수 있습니다. 각 함수 실행은 **여전히 서버에서 동작**하며, 다만 **후속 실행은 다른 서버에서 돌 수 있습니다**.
    
*   게다가 **BigQuery와 여러 Kafka 제공 서비스** 같은 인프라 서비스들도, 자기 서비스가 **오토스케일하고 머신 인스턴스가 아니라 사용량 기준으로 과금한다는 신호**를 주기 위해 "서버리스" 용어를 채택했습니다.

| 논리 단위 ⑦ | 이 책의 관심 범위 한정 |

### ① 전제 — 클라우드는 유일한 답이 아니다

*   대규모 컴퓨팅 시스템 구축 방식으로 **클라우드 컴퓨팅만 있는 것은 아니며**, 대안이 **고성능 컴퓨팅(HPC), 곧 슈퍼컴퓨팅**입니다.
    
*   둘은 **겹치는 부분이 있지만**, HPC는 클라우드 컴퓨팅 및 엔터프라이즈 데이터센터 시스템과 **우선순위가 다르고 사용 기법도 다른 경우가 많습니다**.
    

### ② 대조 1 — 용도(워크로드 성격)

*   **슈퍼컴퓨터**: 계산 집약적 과학 연산에 주로 쓰입니다. 원문이 든 예는 **일기예보, 기후 모델링, 분자 동역학**(원자·분자의 움직임 시뮬레이션), **복잡한 최적화 문제, 편미분방정식 풀이**입니다.
    
*   **클라우드 컴퓨팅**: **온라인 서비스, 비즈니스 데이터 시스템**, 그리고 **높은 가용성으로 사용자 요청을 처리해야 하는** 유사 시스템에 쓰이는 경향이 있습니다.
    

### ③ 대조 2 — 장애 대응 모델 (가장 중요한 차이)

*   **슈퍼컴퓨터**는 대개 **대규모 배치 작업**을 실행하며, 연산 상태를 **주기적으로 디스크에 체크포인트**합니다.
    
*   노드 장애 시 일반적인 해법은 **클러스터 워크로드 전체를 중단 → 결함 노드 수리 → 마지막 체크포인트에서 연산 재시작**입니다 `[54, 55]`.
    
*   **클라우드 서비스**에서는 전체 클러스터를 멈추는 것이 **보통 바람직하지 않습니다**. 서비스가 **중단을 최소화하며 사용자에게 지속적으로 응답해야** 하기 때문입니다.
    

### ④ 대조 3 — 노드 간 통신과 신뢰 가정

*   **슈퍼컴퓨터 노드**는 대개 **공유 메모리와 RDMA**로 통신합니다. 이는 **고대역폭·저지연**을 지원하지만, **시스템 사용자들 사이에 높은 수준의 신뢰를 전제**합니다 `[56]`.
    
*   **클라우드 컴퓨팅**에서는 네트워크와 머신이 **서로 신뢰하지 않는 조직들 간에 공유**되는 경우가 많아, **더 강한 보안 기제**가 필요합니다. 원문이 든 것은 **자원 격리(예: 가상 머신), 암호화, 인증**입니다.
    

### ⑤ 대조 4 — 네트워크 토폴로지

*   **클라우드 데이터센터 네트워크**는 흔히 **IP와 이더넷** 기반이며, **Clos 토폴로지**로 배치해 **높은 bisection 대역폭**을 제공합니다. bisection 대역폭은 **네트워크 전체 성능을 재는 데 흔히 쓰이는 척도**입니다 `[54, 57]`.
    
*   **슈퍼컴퓨터**는 **다차원 메시(mesh)와 토러스(torus)** 같은 **특화된 네트워크 토폴로지**를 자주 사용합니다 `[58]`. 이는 **통신 패턴이 알려진 HPC 워크로드**에서 더 좋은 성능을 냅니다.
    

### ⑥ 대조 5 — 지리적 분산

*   **클라우드 컴퓨팅**은 노드를 **여러 지리적 리전에 분산**할 수 있습니다.
    
*   **슈퍼컴퓨터**는 일반적으로 **모든 노드가 서로 가까이 있다고 가정**합니다.
    

### ⑦ 이 책의 범위 한정

*   **대규모 분석 시스템(large-scale analytical systems)** 은 때때로 슈퍼컴퓨팅과 **일부 특성을 공유**하므로, 그 영역에서 일한다면 이 기법들을 알아둘 가치가 있습니다.
    
*   다만 이 책은 대체로 **지속적으로 가용해야 하는 서비스**를 다루며, 관련 논의는 "Reliability and Fault Tolerance"(p.43)로 연결됩니다.

| --- | --- | --- |
| 주 용도 | 과학 연산(기후·분자동역학·최적화·PDE) | 온라인 서비스, 비즈니스 데이터 시스템 |
| 작업 형태 | 대규모 배치 + 디스크 체크포인트 | 사용자 요청 상시 처리, 고가용성 |
| 노드 장애 대응 | 전체 중단 → 수리 → 체크포인트 재시작 | 전체 중단 불가, 중단 최소화 |
| 노드 간 통신 | 공유 메모리, RDMA (고대역폭·저지연) | IP / 이더넷 |
| 신뢰 모델 | 사용자 간 높은 신뢰 전제 | 상호 불신 조직이 공유 → VM 격리·암호화·인증 |
| 토폴로지 | 다차원 메시, 토러스 (알려진 통신 패턴에 유리) | Clos (높은 bisection 대역폭) |
| 지리 배치 | 노드가 근접해 있다고 가정 | 다중 리전 분산 가능 |

### 두 절을 잇는 논리 흐름

앞 절(Microservices and Serverless)이 **"서비스를 어떻게 쪼개고 배포할 것인가"** 라는 조직·운영 축의 이야기였다면, 이 절은 같은 "여러 머신에 분산한다"는 행위가 **목적에 따라 완전히 다른 설계 전제로 갈라진다**는 점을 보여줍니다. 결정적 분기점은 **연산을 멈춰도 되는지 여부**입니다. 멈춰도 되면 체크포인트–재시작이라는 값싼 내결함성으로 충분하고, 신뢰하는 사용자끼리 RDMA를 열어도 됩니다. 멈출 수 없으면 그 순간부터 결함 허용, 자원 격리, 지리적 분산이 전부 필수가 됩니다. 원문이 마지막에 자기 관심사를 "지속적으로 가용해야 하는 서비스"로 못 박은 것은 이 후자 계열을 책의 기본 전제로 선언한 것입니다.

# IV. Data Systems, Law, and Society (p.24–25)

## IV-0. 이 절이 주장하는 다섯 개 명제

| # | 명제 | 근거가 되는 원문 지점 |
| --- | --- | --- |
| 1 | 엔지니어의 책임은 자기 사업을 넘어 사회로 확장된다 | 도입부 |
| 2 | 법은 이미 설계의 근본을 바꾸고 있다 (삭제권 vs 불변 로그) | GDPR 잊힐 권리 |
| 3 | 무엇이 준수인지 알려주는 기술 명세는 존재하지 않는다 | 규제의 기술 중립성 |
| 4 | 저장 비용은 청구서가 아니라 배상·벌금·사용자 안전까지다 | 확장된 손익 계산 |
| 5 | 따라서 최소 수집이 윤리 권고가 아니라 비용 최적해다 | Datensparsamkeit |

## IV-1. 책임의 확장

*   데이터 시스템 아키텍처는 기술적 목표·요구뿐 아니라 **그것을 지탱하는 조직의 인간적 필요**에도 좌우됩니다.
    
*   엔지니어들은 **자기 사업의 필요 충족만으로는 부족하며 사회 전체에 대한 책임도 있다**는 점을 점점 인식하고 있습니다.
    
*   특히 우려되는 대상은 **사람과 그 행동에 관한 데이터를 저장하는 시스템**입니다.
    

## IV-2. 규제 — 세 층

*   **GDPR (2018년 이후)**: 다수 유럽 국가 거주자에게 개인 데이터에 대한 **더 큰 통제권과 법적 권리**를 부여.
    
*   **유사 규제의 확산**: 세계 여러 국가·주가 유사 프라이버시 규제를 채택(예: **CCPA**).
    
*   **AI 규제**: **EU AI Act** 등이 개인 데이터 사용 방식에 **추가 제약**을 부과.
    

## IV-3. 규제가 닿지 않는 영역의 파급력

*   직접 규제 대상이 아닌 영역에서도 시스템이 사람과 사회에 미치는 영향에 대한 인식이 커지고 있습니다.
    
*   **소셜 미디어** → 뉴스 소비 방식 변화 → **정치적 견해에 영향** → **선거 결과에까지 영향 가능**.
    
*   **자동화된 결정**이 개인에게 심대한 결과를 낳는 사례 네 가지: **대출 승인, 보험 보장, 면접 초대, 범죄 용의자 지목** `[59]`.
    

## IV-4. 요구되는 소양의 수준 — 원문의 기준선

*   그런 시스템에서 일하는 **모든 사람**이 자기 결정의 윤리적 영향을 고려하고 법 준수를 확인할 책임을 나눠 갖습니다.
    
*   **모두가 법·윤리 전문가가 될 필요는 없습니다.** 그러나 기본적 인식은 **"분산 시스템의 기초 지식만큼" 중요**합니다. 원문이 직접 세운 비교 기준입니다.
    

## IV-5. 법이 설계를 흔드는 구체적 충돌

*   법적 고려가 **데이터 시스템 설계의 근본 자체에 영향**을 주고 있습니다 `[60]`.
    
*   **한쪽**: GDPR이 부여한 **요청 시 삭제받을 권리**(잊힐 권리).
    
*   **다른 쪽**: 많은 데이터 시스템이 **append-only 로그 같은 불변 구성물**을 설계의 일부로 사용.
    
*   여기서 파생되는 **두 개의 미해결 질문**: 불변이어야 하는 **파일 중간의 특정 데이터 삭제를 어떻게 보장**하는가, 그리고 **파생 데이터셋에 편입된 데이터**의 삭제는 어떻게 처리하는가 — 예: **ML 모델 학습 데이터**(참조: "Systems of Record and Derived Data", p.10).
    
*   이 답을 찾는 일이 **새로운 엔지니어링 과제**를 만들어 냅니다.
    

## IV-6. 준수 판단의 공백

*   **어떤 기술이나 아키텍처가 GDPR 준수로 간주되는지에 대한 명확한 지침이 현재 없습니다.**
    
*   규제는 **의도적으로** 특정 기술을 의무화하지 않습니다. 기술은 발전하면서 빠르게 변할 수 있기 때문입니다.
    
*   대신 법 조문은 **해석의 여지가 있는 고수준 원칙**을 제시합니다. 그래서 준수 방법에는 **단순한 답이 없고**, 책은 기술들을 이 렌즈로 검토하는 방식을 택합니다.
    

## IV-7. 저장의 실제 비용 — 네 항목

우리는 데이터의 **가치가 저장 비용보다 크다고 판단해서** 저장합니다. 그런데 비용은 **S3 청구서를 넘어섭니다** `[50]`.

*   ① 서비스 이용료(청구서).
    
*   ② 유출·침해 시 **책임(liability)** 위험.
    
*   ③ 유출·침해 시 **명성 훼손** 위험.
    
*   ④ 저장·처리가 위법으로 판정될 때의 **법적 비용과 벌금**.
    

## IV-8. 데이터가 안전 위험이 되는 경우

*   **정부나 경찰이 기업에 데이터 제출을 강제**할 수 있습니다.
    
*   데이터가 **범죄화된 행위**를 드러낼 수 있을 때, 저장 자체가 사용자에게 **실질적 안전 위험**을 만듭니다. 원문의 예: **일부 중동·아프리카 국가의 동성애**, **미국 여러 주의 낙태 시도**.
    
*   **누출 경로의 구체성**: 낙태 시술소로의 이동은 **위치 데이터**로 드러날 수 있고, 심지어 **시간에 따른 IP 주소 로그**(대략적 위치를 시사)만으로도 드러날 수 있습니다.
    

## IV-9. 데이터 최소화 (Datensparsamkeit)

*   위험을 모두 반영하면 **어떤 데이터는 저장할 가치가 없으므로 삭제해야 한다**는 판단이 합당할 수 있습니다.
    
*   이 원칙은 **"장차 유용할지 몰라 추측적으로 대량 저장"하는 빅데이터 철학과 정면 대립**합니다 `[61]`.
    
*   반대로 **GDPR과는 부합**합니다. GDPR이 개인 데이터에 부과하는 **세 가지 의무** `[62]`: **명시되고 명확한 목적**을 위해서만 수집 가능, 이후 **다른 어떤 목적으로도 사용 불가**, 수집 목적에 **필요한 기간을 넘겨 보관 금지**.
    

## IV-10. 업계 자율 규범 — 두 표준

*   **PCI (Payment Card Industry)**: 신용카드 회사가 결제 처리업체에 엄격한 준수를 요구하며, 처리업체는 **독립 감사인의 빈번한 평가**로 지속 준수를 검증받습니다.
    
*   **SOC Type 2 (Service Organization Control)**: 소프트웨어 벤더 검증이 강화되어 **많은 구매자가 벤더에게 준수를 요구**하고, PCI와 마찬가지로 **제3자 감사**로 확인합니다.
    
*   결론: **사업의 필요와 데이터 주체의 필요 사이 균형**이 중요합니다. 상세는 **Chapter 14** — **편향과 차별 문제 포함**.

## 되짚은 네 축

| 축 | 원문의 결론 | 이후 참조 |

| OLTP vs OLAP | 접근 패턴이 다른 데이터를 관리한다는 점만이 아니라 **서로 다른 청중에게 서비스**한다는 점에서도 다름. 그 과정에서 **데이터 웨어하우스·데이터 레이크** 개념을 만났고, 이들은 **ETL로 운영 시스템에서 피드를 받음** | Ch.4 — 처리할 쿼리 유형이 달라 **내부 데이터 레이아웃이 매우 다름** |
| 클라우드 vs 자체 호스팅 | 어느 쪽이 비용 효율적인지는 **상황에 크게 의존**. 다만 클라우드 네이티브가 아키텍처 방식에 **큰 변화를 가져오는 것은 부인 불가** — 예: **스토리지와 컴퓨트의 분리** | — |

| 법·프라이버시 | 아키텍처는 **배포하는 사업의 필요만이 아니라** 데이터 주체의 권리를 보호하는 **프라이버시 규제에 의해서도 결정**됨. 원문은 이를 **많은 엔지니어가 무시하기 쉬운 측면**이라고 명시. **법적 요구를 기술 구현으로 옮기는 방법은 아직 정형화되지 않음** | 책 전체를 통해 염두에 둘 질문 |

## 절 하나로 압축한 마지막 절의 의미

앞의 세 축은 엔지니어가 **고를 수 있는** 트레이드오프였습니다. 마지막 절은 거기에 **고를 수 없는 제약**을 얹습니다. 삭제권과 불변 로그의 충돌이 그 축약판입니다. 한쪽은 법이, 다른 쪽은 성능과 단순성이 요구하는데 어느 기술이 준수인지 말해주는 명세는 없습니다. 규제를 기술 중립적으로 쓴 대가입니다. 그래서 이 절의 실천적 산출물은 기술이 아니라 **계산 규칙**입니다. 저장 여부의 손익에 배상·벌금·사용자의 신체적 안전까지 넣고 나면, 상당량의 데이터는 **아예 수집하지 않는 것이 가장 값싼 아키텍처**가 됩니다. Datensparsamkeit이 도덕적 권고가 아니라 **원가 계산의 결론**으로 배치된 것이 이 절의 설계 의도입니다.
