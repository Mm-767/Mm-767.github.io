## 1\. 개요와 범위

### 1.1 목적

HQ는 사용자의 생활 패턴을 분석해 가장 부담 없는 행동을 제안하고, 루틴이 무너져도 점진적으로 복귀시키는 AI 웰니스 서비스다. 이 문서는 그 제품 요구사항을 **어떤 기술 구조로 구현할 것인지**와 **왜 그 선택인지**를 기술한다.

무엇을 만들지는 PRD, 시스템이 만족해야 할 조건은 SRS가 다룬다. 이 문서는 구현 수단만 다룬다.

### 1.2 대상 기능

| 기능 | 상태 | 이 문서에서 다루는 범위 |
| --- | --- | --- |
| ① AI 루틴 설계 | \[확정\] | 2·5·6장 |
| ② 이상치 패턴 감지 (Green/Yellow/Red) | \[확정\] | 4·6장 |
| ③ 점진적 루틴 복귀 | \[확정\] | 4·6장 |
| 일정/플래너 연동 | \[확정\] | 5.4 외부 연동 |
| ④ 4주간 웰니스 리포트 | \[미결\] | 범위 밖 — 위상 미확정 |
| ⑤ AI 챗봇 | \[미결\] | 범위 밖 — 위상 미확정 |

회의록 7장에는 ④·⑤가 핵심 기능으로 적혀 있으나 설명이 없고, 결정사항 D4는 "핵심 기능 3가지 확정"으로 남아 있다. 두 기능은 AI 추론 구조를 크게 바꾸므로(특히 챗봇은 "생성형보다 RAG 우선" 방침과 직결) **위상이 정해지기 전까지 이 문서의 범위에 넣지 않는다.**

### 1.3 범위 밖

*   AAC 오프라인 서비스 연동 — 선택형 모듈이며 실제 AAC 데이터 사용은 불가로 확인됨. 스키마 확장 지점만 열어둔다(9.2 참조)
    
*   보상 체계, 캐릭터 성장, SNS 공유 등 서브 기능 후보
    
*   관리자 백오피스

## 2\. 시스템 아키텍처

### 2.1 구성

```
        [ 클라이언트 ]
              │  HTTPS / JWT
              ▼
   ┌──────────────────────┐        ┌──────────────────────┐
   │  Spring Boot (Main)  │◄─REST─►│   FastAPI (AI/ML)    │
   │  인증 · CRUD · 트랜잭션  │        │ 루틴생성 · 추천 · 판정   │
   └──────────┬───────────┘        └──────────┬───────────┘
              │ 읽기+쓰기 (Flyway 소유)           │ 읽기 전용
              │                                │ + adjustments INSERT
              ▼                                ▼
           ┌────────────────────────────────────┐
           │          PostgreSQL                │
           └────────────────────────────────────┘
                            │
              외부 API: OpenAI · 카카오맵 · 캘린더
```

### 2.2 컴포넌트 책임

| 컴포넌트 | 책임 | 하지 않는 것 |
| --- | --- | --- |
| 클라이언트 | 화면, 최소 입력 수집, 로컬 알림 | 판정 로직, 난이도 계산 |
| Spring Boot | OAuth 인증, JWT 발급·검증, 도메인 CRUD, 트랜잭션, 스키마 마이그레이션 | AI 추론, `routine_tasks.action_id` 직접 UPDATE |
| FastAPI | 루틴 초안 생성, 행동 추천, 이상치 패턴 판정 | 스키마 변경, 일반 테이블 쓰기 |
| PostgreSQL | 저장 + 무결성 + 난이도 적용 트리거 | 인가(RLS 미사용) |

### 2.3 서비스 경계가 이 구조인 이유

FastAPI에 별도 DB 롤을 만들어 `GRANT SELECT`만 부여하고, 쓰기는 `adjustments` INSERT 하나만 허용한다. 추천 서비스가 `task_logs`를 실수로 오염시키는 사고를 애플리케이션 코드가 아니라 **DB 권한으로** 막기 위해서다.

난이도 조정의 유일한 입구도 `adjustments` INSERT다. 트리거가 실제 적용을 수행하므로 Spring이 `routine_tasks.action_id`를 직접 쓰면 이중 적용이 된다. 이 제약은 시연 방식과도 맞물려 있다 — 심사 자리에서 psql로 `insert into adjustments` 한 줄을 실행해 난이도 하향을 보여주기로 확정했다.

### 2.4 클라이언트 기술 — **\[미결·최우선\]**

아키텍처 표는 **Flutter**로 되어 있으나, 회의록 10장의 결정은 **PWA 우선 검토**다. 두 결정이 충돌한다.

|  | Flutter | PWA |
| --- | --- | --- |
| 시연 | 빌드·설치 필요 | URL 하나로 즉시 |
| 개발 효율 | 팀 숙련도 확인 필요 | 웹 기술 재사용 |
| 위젯 기록 (미결 3번) | 네이티브 위젯 가능 | **불가** |
| 스크린타임 등 행동 데이터 (미결 2번) | 플랫폼 API 접근 가능 | **불가** |

**이 선택은 미결 2번·3번의 답을 사실상 결정한다.** PWA로 가면 이상치 패턴 감지의 입력이 앱 내 기록으로 한정되고, `users.last_active_at` 같은 서버 측 신호에 더 의존하게 된다. 8/4 회의에서 반드시 정해야 하며, 그 전까지 이 문서의 클라이언트 관련 서술은 확정이 아니다.

## 4\. 데이터 설계

상세 DDL과 설계 근거는 `hq-db-design.md`(v0.5), ERD는 `hq-erd.md`, 검토 기록은 `hq-db-design-v0.5-review.md`에 있다. 여기서는 TRD 관점의 요약만 둔다.

### 4.1 구조

**6 테이블 + 뷰 2개 + 트리거 3개.**

| 층 | 대상 | 대응 기능 |
| --- | --- | --- |
| 정의 — 무엇을 하기로 했나 | `actions` `routines` `routine_tasks` | ① 루틴 설계 |
| 실행 — 실제로 했나 | `task_logs` | 최소 입력 원칙 |
| 판정 — 지금 어떤 상태인가 | `v_daily_states` `adjustments` | ② 이상치 패턴 ③ 점진적 복귀 |

`users`는 이 세 층 전체가 참조한다.

### 4.2 TRD 관점에서 중요한 세 가지

**난이도가 사다리 위의 좌표다.** `actions.ladder_key`로 묶인 행들이 `level`(10, 20, 30 — 간격 10이라 중간 삽입 가능)로 정렬되고, 난이도 조절은 이 사다리 위 이동으로 표현된다. 점진적 복귀 기능이 곧 이 구조다.

**과거 기록은 동결된다.** `task_logs.action_id`가 그날의 난이도 스냅샷을 따로 들고 있어, 난이도를 낮춰도 과거 기록의 의미가 소급 변경되지 않는다. "최근 수행 추세" 계산의 기준선이 유지되어야 하기 때문이다. `trg_freeze_log_snapshot`이 스냅샷 컬럼 UPDATE를 거부한다.

**판정 결과를 저장하지 않는다.** `v_daily_states`는 실테이블이 아닌 뷰다. Green/Yellow/Red 컷오프가 미확정이라, 뷰로 두면 숫자만 고쳐도 과거까지 즉시 재판정된다.

### 4.3 인가는 애플리케이션 책임

RLS를 쓰지 않으므로 `user_id` 조건이 빠진 쿼리 하나가 전체 사용자 데이터 노출로 이어진다. 리포지토리 조회 메서드 시그니처에 `userId`를 필수 파라미터로 두고, **통합 테스트에 타인 데이터 조회 시도 케이스를 반드시 포함한다.** (7.2 참조)

## 5\. API 설계 — \[검토\]

이 장 전체가 스키마에서 도출한 초안이며 팀 리뷰 전이다.

### 5.1 인증

| 단계 | 처리 |
| --- | --- |
| 소셜 로그인 | 클라이언트가 provider(kakao/google/apple) 인가 코드 획득 |
| 토큰 교환 | `POST /auth/{provider}` → Spring이 검증 후 자체 JWT 발급 |
| 사용자 식별 | JWT `sub` 클레임 = `users.id`(uuid) |
| 갱신 | Refresh 토큰 방식 **\[미결\]** — 만료·폐기 정책 미정 |

### 5.2 주요 엔드포인트 (Spring Boot)

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| `POST` | `/auth/{provider}` | 소셜 로그인, JWT 발급 |
| `POST` | `/onboarding` | 온보딩 응답 저장 (`users.onboarding` jsonb) |
| `GET` | `/routines` | 내 루틴 목록 (archived 제외) |
| `POST` | `/routines` | 루틴 생성 — FastAPI 초안을 받아 확정 저장 |
| `PATCH` | `/routines/{id}` | 제목·요일·상태 변경 |
| `GET` | `/today` | 오늘의 태스크 목록 + 현재 신호등 |
| `POST` | `/logs` | 수행 기록 — `routine_task_id`, `status`, `done_count`**만** 전송 |
| `GET` | `/states?from=&to=` | 기간별 일일 상태 (`v_daily_states`) |
| `GET` | `/adjustments` | 난이도 변경 이력 + `reason` 문구 |

`POST /logs`가 세 필드만 받는 것은 최소 입력 원칙의 구현이다. `user_id`·`action_id`·`target_count`·`scheduled_at`은 `trg_fill_log_snapshot`이 채우므로 클라이언트가 보내지 않는다.

### 5.3 서버 간 통신 (Spring ↔ FastAPI)

| 메서드 | 경로 | 요청 | 응답 |
| --- | --- | --- | --- |
| `POST` | `/ai/routines/draft` | 목표, 생활 패턴, 온보딩 요약 | 루틴 초안 (actions 참조 배열) |
| `POST` | `/ai/recommendations` | user\_id, 최근 상태 | 추천 행동 목록 |
| `POST` | `/ai/signal/evaluate` | user\_id, 기간 | 신호 판정 + 조정 제안 |

프로토콜은 REST로 시작한다. **\[검토\]** 초안의 gRPC는 팀 규모와 일정 대비 이득이 크지 않다고 판단했다.

FastAPI는 판정 결과를 응답으로만 돌려주고, 난이도 조정이 필요하면 `adjustments`에 INSERT한다. 그 외 테이블에는 쓰지 않는다.

### 5.4 외부 연동

| 대상 | 용도 | 상태 |
| --- | --- | --- |
| OpenAI API | 원인 추론, 패턴 요약 (Structured Outputs) | \[검토\] |
| 카카오맵 Local | 좌표 기반 근처 행동 추천 | \[검토\] |
| 캘린더 (일정/플래너 연동) | 루틴 배치 기준이 되는 일정 확보 | **\[미결\]** — 연동 대상 서비스 미정 |

캘린더 연동은 확정된 서브 기능이지만 대상(Google Calendar / Apple / 자체 입력)이 정해지지 않았다. 이 선택도 2.4의 클라이언트 결정에 종속된다.

## 6\. AI 파이프라인

### 6.1 원칙

생성형 AI보다 **기존 데이터 기반 추천(RAG 포함)을 우선**한다. LLM은 자유 생성이 아니라 이미 정의된 `actions` 라이브러리에서 고르고 그 이유를 설명하는 역할에 둔다. Structured Outputs로 출력 스키마를 강제해 존재하지 않는 action이 생성되는 것을 막는다.

### 6.2 ① 루틴 설계

```
온보딩 + 목표 + wake_at/sleep_at
   → actions 라이브러리 후보 필터 (category, level 하한)
   → v_action_priors 로 콜드스타트 보정 (신규 가입자)
   → LLM이 조합·배치 (Structured Outputs)
   → routine_tasks 초안 반환 → 사용자 확인 → Spring이 저장
```

신규 가입자는 개인 이력이 없으므로 `v_action_priors`(전역 `task_logs` 집계, 라플라스 보정)로 "대체로 잘 지켜지는 행동"을 우선 배치한다.

### 6.3 ② 이상치 패턴 감지

`v_daily_states`가 `completion_rate`를 산출하고, 컷오프에 따라 Green/Yellow/Red를 판정한다. `users.last_active_at`이 핵심 보조 피처다 — **로그 0행이 곧 이탈은 아니기 때문**이다(앱을 열었으나 기록하지 않은 경우와 구분).

**\[미결\]** 컷오프가 확정되지 않았다. 현재 0.7 기준이면 태스크 3개 루틴에서 2개를 수행해도 yellow가 된다. **\[미결\]** `gray`(판정 불가) 4번째 상태 도입 여부는 기획 승인이 필요하다.

### 6.4 ③ 점진적 복귀

```
red 신호 또는 연속 성공 감지
   → 같은 ladder_key 내 인접 level 선정
   → 사용자 노출 문구(reason) 생성
   → adjustments INSERT → 트리거가 적용
```

`adjustments.reason`은 로그가 아니라 **사용자에게 보여줄 문구**다. 사다리 교차, 낡은 근거, 보관된 태스크는 `trg_apply_adjustment`가 거부한다.

## 7\. 비기능 요구사항

측정 가능한 목표치는 SRS에 두고, 여기서는 달성 수단을 기술한다.

### 7.1 성능

| 항목 | 수단 |
| --- | --- |
| `GET /today` 응답 | 인덱스 기반 단일 쿼리. 판정은 뷰에서 즉시 계산 |
| AI 루틴 생성 | 동기 호출 시 수 초 소요 예상 → **\[검토\]** 비동기 + 폴링 |
| 목표 수치 | **\[미결\]** SRS와 함께 확정 |

### 7.2 보안

| 항목 | 수단 |
| --- | --- |
| 인가 | Spring Security. 모든 조회에 `userId` 강제 (4.3) |
| DB 권한 분리 | FastAPI 롤은 SELECT + `adjustments` INSERT만 |
| 전송 | 전 구간 HTTPS |
| 토큰 | JWT 서명 검증, 만료 정책 **\[미결\]** |
| 비밀 정보 | 환경변수 주입, 코드에 하드코딩 금지 |

### 7.3 개인정보

`users.consent` jsonb에 `{version, granted_at}`을 기록한다. **\[미결\]** 회의 미결 1·2번(수집 항목과 동의 범위, 행동 데이터 소스와 프라이버시)이 정해져야 이 장을 완성할 수 있다. 건강 관련 데이터를 다루므로 수집 항목이 정해지는 즉시 법적 요구사항을 재검토한다.

### 7.4 데이터 무결성

하드 삭제를 금지하고 `archived_at` 소프트 삭제를 쓴다. 태스크를 하드 삭제하면 과거 `task_logs`가 사라지고 완료율의 분모가 소급 변한다.

삭제 연쇄는 `users` → `routines` → `routine_tasks`가 cascade, `task_logs`·`adjustments`는 `no action`이다. `restrict`**를 쓰면 안 된다** — 즉시 검사라 cascade 도중에 걸려 회원 탈퇴 DELETE가 영구 실패한다(v0.4에서 실제로 발생).

## 9\. 리스크와 미결 사항

### 9.1 기술 리스크

**FAISS가 지금 필요한가 — 재검토 권고.** 벡터 검색의 두 용도가 이미 다른 수단으로 덮인다. 최소 행동 라이브러리 검색은 `actions`가 수십 행 규모라 `category` + `ladder_key` 필터로 충분하고, 유사 패턴 매칭은 `v_action_priors` 집계가 콜드스타트를 담당한다. 별도 인덱스 파일의 생성·저장·동기화 비용이 8/4~시연 일정에서 회수되지 않을 가능성이 높다. **필요해지면 pgvector로 PostgreSQL 안에서 해결하는 편이 인프라를 늘리지 않는다.**

**LangChain도 같은 질문을 받는다.** 파이프라인이 6.2 수준의 단계 수라면 OpenAI SDK 직접 호출이 디버깅하기 쉽다. 도입한다면 "무엇을 대신 해주는가"를 답할 수 있어야 한다.

**서버 2개 운영 비용.** Spring + FastAPI 분리는 AI 생태계 때문이지만, 배포·로깅·장애 대응이 두 배가 된다. 일정이 촉박하면 초기에는 단일 배포 단위로 묶고 경계만 코드로 유지하는 선택지가 있다.

**OpenAI API 의존.** 지연·비용·장애가 그대로 사용자 경험이 된다. 루틴 생성 실패 시 `v_action_priors` 기반 규칙 추천으로 폴백하는 경로를 두면 시연 중 API 장애에도 화면이 비지 않는다.

### 9.3 용어 통일

기능 ②의 정식 명칭은 \*\*"이상치 패턴 감지"\*\*다. 회의록 최종본은 "이탈 신호 감지"로 표기되어 있으나 DB 설계 문서(v0.5)는 "이상치 패턴"을 쓰고 있다. PRD·TRD·SRS가 서로 다른 이름을 쓰지 않도록 8/4 회의에서 하나로 확정한다.

또한 '무기력증', '실행기능 저하' 등 정신건강 진단으로 오해될 표현은 모든 문서에서 사용하지 않는다(D2).
