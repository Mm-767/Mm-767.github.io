상태: 채택 · ADR-002의 범위를 좁힘

## 문제

일일 미션("어제 42분 → 오늘 32분")이 언제, 어디서 계산되고, 알림(P0)과 어떻게 맞물릴지.

제약: "미션 할당 시 알림"이 P0 → 알림 내용이 사용자가 앱을 열기 전에 이미 존재해야 함. ADR-002에서 FastAPI는 상시 배포하지 않기로 함(데모 주만) → FastAPI는 스스로 새벽에 깨어날 수 없음. Supabase의 Postgres 자체는 FastAPI와 무관하게 24시간 가동 → pg_cron으로 DB 안에서 스케줄 가능.

## 검토한 선택지

| 안 | 시점 | 로직 위치 | 알림 순서 | 상시 가동 필요 |
|---|---|---|---|---|
| A. 새벽 배치 + SQL(pg_cron) | 매일 06:00 전체 유저 일괄 | Postgres 함수 | 성립(내용 미리 있음) | 불필요(DB는 항상 켜짐) |
| B. 온디맨드 + FastAPI | 앱 여는 순간 | 파이썬 | 불성립(알림 먼저 못 보냄) | FastAPI가 그 순간 깨어있어야 |
| C. 온디맨드 + SQL RPC | 앱 여는 순간 | Postgres 함수 | 불성립 | 불필요 |
| D. 새벽 배치 + FastAPI 스케줄러 | 매일 06:00 | 파이썬 | 성립 | FastAPI 상시 필요(ADR-002 위반) |

## 결정

A. `pg_cron`이 매일 06:00 Postgres 함수를 호출해 전체 유저의 오늘 미션을 미리 생성한다(어제 daily_usage 합 - 10분, 최소 15분). 계산 로직은 SQL. 사용자가 앱을 열면 이미 만들어진 미션을 읽기만 한다.

## 근거

- P0 요구사항("미션 알림"이 "내용이 미리 있어야 알림 가능"을 요구) → 배치가 온디맨드보다 제품 요구사항에 맞다.
- Postgres는 FastAPI 배포 여부와 무관하게 항상 켜져 있어 pg_cron이 안정적으로 돈다.
- 지금 규칙("어제-10분, 최소 15분")이 SQL 한 줄로 충분히 표현된다.
- 다른 습관형 앱(듀오링고류)도 일일 콘텐츠를 새벽 배치로 미리 만들어두는 패턴을 씀 — 검증된 방식.

## 포기한 것

- ADR-002가 FastAPI 몫으로 남겨뒀던 "미션 추천"이 이 결정으로 SQL로 이동한다. FastAPI의 남은 일은 주간 리포트 하나뿐.
- 규칙이 복잡해지면(사용 패턴 분석, 요일별 가중치 등) SQL 함수 안에서 하기 괴로워질 수 있다. 그땐 pg_cron이 FastAPI 엔드포인트를 HTTP로 호출하는 방식(`net.http_post`)으로 옮기면 된다.

## 당시 몰랐던 것

- 실제 알림 발송(FCM/푸시) 주체가 아직 미정 — pg_cron이 미션을 만든 다음 알림을 누가/어떻게 보내는지는 별도 결정 필요 (→ [ADR-18](/posts/adr-18-미션-알림-발송-주체-supabase-edge-function-supabase-cron-jobs)에서 결정).
- pg_cron이 Supabase 무료 티어에서 별도 제한이 있는지 미확인.
- 유저 수가 늘었을 때 "전체 유저 순회"가 06:00 배치 창 안에 끝나는지 미검증(해커톤 규모엔 무관).
