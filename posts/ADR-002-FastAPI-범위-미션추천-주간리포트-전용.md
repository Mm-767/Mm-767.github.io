상태: 채택 · ADR-001에 이어짐

## 문제

PETOX의 서버 로직을 어디에 둘까. Supabase 위에서 로직 둘 자리가 셋 — Postgres 함수(RPC, SQL) / Edge Function(Deno, TypeScript) / 별도 FastAPI(Python).

제약: 3주 / BE 1명 / 무료 유지 / FastAPI를 배우고 싶음 / 코인·구매는 조작 방지 필요.

서버 로직 목록:
- 미션 완료 시 코인 지급, 아이템 구매, 펫 슬롯 구매 — 원자적·조작 방지
- 미션 판정(오늘 사용 ≤ 목표?) — 자정 배치 또는 읽을 때 계산
- 일일 미션 추천("어제 42분 → 오늘 30분") — 어제 데이터 보고 로직
- 주간 리포트 생성 — 일주일치 집계 + 문구

## 검토한 선택지

| 안 | FastAPI가 맡는 것 | 배포 | FastAPI 학습 | 조작 방지 | 일정 리스크 |
|---|---|---|---|---|---|
| A. 추천·리포트 전용 | 미션 추천 + 주간 리포트 (2~3개) | 데모 주만 무료 호스팅 | 핵심만 유지 | RPC가 담당 | 낮음 |
| B. 전체 백엔드 | 신뢰 로직 포함 전부 | 상시 배포 | 많음 | FastAPI 트랜잭션 직접 관리 | 중간 (콜드스타트·비용) |
| C. FastAPI 없음 | 없음 | 없음 | 0 | RPC + Edge Function(TS) | 낮음 |

## 결정

A. FastAPI는 미션 추천 + 주간 리포트만 담당. 원자적 신뢰 처리(코인 지급·아이템 구매·펫 슬롯)는 Postgres 함수(RPC). 개발 중엔 FastAPI를 로컬로 돌리고, 대회 마지막 주에만 무료 호스팅(Render 등)에 올려 데모 전 워밍업.

## 근거

- 원자적 신뢰 처리는 RPC가 정답이다. `SELECT buy_item(item_id)` 한 번에 "코인 확인 → 차감 → 지급"이 트랜잭션으로 묶인다. FastAPI로 같은 걸 하면 트랜잭션을 직접 관리해야 하고 실수 여지가 크다.
- 미션 추천·주간 리포트는 집계·추천 로직이라 SQL보다 파이썬이 확실히 편하다. FastAPI가 여기 딱 맞는다.
- FastAPI 표면이 작아서 3주 안에 제대로 만들고 테스트할 수 있다. CRUD 20개를 다 짜는 B는 일정에 위험하다.
- 상시 배포가 없으니 비용 0, 콜드스타트는 데모 워밍업으로 회피.

## 포기한 것

- "FastAPI 백엔드를 통째로 만들었다"는 제출물 임팩트. FastAPI가 작아 존재감이 약하다.
- 시스템이 둘로 나뉜다 — RPC(SQL)와 FastAPI(Python)를 둘 다 관리. 로직이 어디 있는지 헷갈릴 수 있다.
- 단일 API 표면 포기 — 클라이언트가 Supabase SDK·RPC·FastAPI를 상황따라 호출.

## 당시 몰랐던 것

- "추천·리포트만 FastAPI" 경계가 실제로 안 무너질지. 미션 판정이 사용로그와 얽히면 FastAPI로 흘러들 수 있다.
- Render 무료 티어 콜드스타트(15분 유휴 후 ~30~50초)가 데모에서 정말 워밍업으로 감당되는지 미검증.
- 미션 추천 로직이 얼마나 복잡해질지. 단순 규칙이면 pg_cron으로도 충분해서 FastAPI가 더 얇아질 수 있다.

## 결과

> **추기 (2026-09-11, ADR-005 결정 이후)**: FR-057(미션 알림, P0)이 "알림 내용이 사용자가 앱을 열기 전에 이미 있어야 함"을 요구한다는 게 드러나면서, 미션 생성은 새벽 배치(pg_cron)로 가야 했고 배치는 FastAPI가 상시 켜져 있어야만 가능해 이 ADR의 전제("FastAPI 상시 배포 안 함")와 충돌했다. 그래서 미션 추천 로직을 SQL(Postgres 함수)로 옮겼다 — 자세한 내용은 ADR-005. 이 ADR의 나머지 결정(신뢰 로직은 RPC, FastAPI 상시 배포 안 함)은 그대로 유지되고, FastAPI의 실제 범위는 주간 리포트 하나로 좁혀졌다. 당시 몰랐던 것 칸의 "단순 규칙이면 pg_cron으로도 충분해서 FastAPI가 더 얇아질 수 있다"가 실제로 일어난 셈.
