상태: 채택 · ADR-002·ADR-005의 연장선

## 문제

ADR-002가 FastAPI에 남긴 두 기능(미션 추천, 주간 리포트) 중 미션 추천은 ADR-005로 이미 SQL(pg_cron 배치)로 넘어갔다. 그 결과 FastAPI에 실제로 남은 일은 주간 리포트(`GET /reports/weekly`) 하나뿐인데, "지난주 vs 이번주 앱 사용 시간 비교 분석"을 계산하는 로직을 SQL에 둘지 Python(FastAPI)에 둘지가 아직 정해지지 않았다. 이 결정은 ADR-005의 연장선이다 — 리포트마저 SQL로 넘기면 "FastAPI가 왜 필요한가"(ADR-002의 존재 이유)라는 질문이 다시 열린다.

제약: 해커톤 규모(사용자 수십 명, 유저당 주간 daily_usage row는 최대 42개 — 앱 3종 × 14일), JWT 인증(ADR-010)이 아직 구현 전.

## 검토한 선택지

| 안 | 집계 위치 | 네트워크로 넘어오는 데이터 | ADR-002 취지 부합 |
|---|---|---|---|
| A. FastAPI에서 전부 집계 | Python(원본 row를 가져와 for문으로 합산) | 원본 row 전부(최대 42개) | 높음 |
| B. SQL RPC가 전부 집계, FastAPI는 포맷만 | Postgres 함수(GROUP BY) | 집계된 결과만(2줄) | 낮음 — ADR-005처럼 FastAPI 존재 이유 약화 |
| C. SQL은 기본 합계만, FastAPI가 비교%·문구 생성 | 혼합 | 집계된 합계만 | 중간~높음 |

## 결정

C. daily_usage의 지난주/이번주 합계는 Postgres SQL 함수(GROUP BY)가 계산하고, FastAPI는 그 두 숫자를 받아 몇 % 줄었는지, 어떤 문구를 보여줄지 같은 해석·표현 로직만 담당한다.

## 근거

**A와 B의 차이를 먼저 실제로 재현해서 확인했다.** daily_usage를 흉내낸 로컬 예시(지난주 7일치 사용량, 이번주 7일치)를 놓고 두 방식을 그대로 돌려봤다.

- A안(파이썬 집계): `SELECT * ...`로 14개 row를 그대로 받아와서, 파이썬 for문으로 "지난주 합계"와 "이번주 합계"를 각각 더했다. 결과: 지난주 385분, 이번주 260분.
- B안(SQL 집계): GROUP BY로 이미 더해진 2줄만 받았다.

같은 정답이 나왔지만, 네트워크로 넘어오는 데이터 모양이 14개 row 대 2개 row로 완전히 다르다. 비유하면 B는 계산대 점원이 잔돈을 세서 "3,850원입니다" 하고 건네주는 것이고, A는 동전 한 움큼을 그대로 건네며 "네가 세봐"라고 하는 것과 같다 — 최종 금액은 같아도 누가 세는 수고를 하느냐가 다르다.

**"그럼 SQL이 항상 빠른 거 아니냐"는 질문에는 아니라고 답했다.** 지금 규모(유저 1명당 최대 42개 row)에서는 파이썬이 순회하는 시간이 사실상 0이라, 체감 속도 차이가 없다. 이 결정은 성능 문제가 아니라 "계산 로직을 SQL(선언형)에 둘 것이냐 파이썬(명령형)에 둘 것이냐"의 문제였다.

**이 축을 다시 정리하면:** SQL(선언형)은 "결과가 뭐여야 하는지"만 말하면 엔진이 계산을 대신 해주니 정확성 책임이 엔진으로 넘어가고(버그 여지가 적음), 대신 그 계산을 고치려면 새 마이그레이션 + PR + CI를 거쳐야 한다. 파이썬(명령형)은 계산을 직접 코드로 써야 하니 정확성 책임이 개발자에게 남고(버그 여지가 있음), 대신 코드 한 줄 고치고 재배포하면 바로 반영된다.

이 "버그 여지"는 추상적인 얘기가 아니라 실제로 데모 코드에서 거의 사고를 낼 뻔했다. 파이썬 집계 코드에서 날짜를 문자열로 비교했는데(`d < '2026-09-08'`), 만약 날짜 문자열에 자릿수가 안 맞는 값('2026-09-8'처럼 0 없이)이 섞이면 문자열 비교가 사전순으로 어긋나서 조용히 틀린 답을 낼 수 있었다 — 이번엔 운 좋게 결과가 맞았지만, 이게 정확히 A안(직접 순회 로직)에서 실제로 터질 수 있는 버그 유형이다. SQL의 GROUP BY와 DATE 타입 비교는 이런 문자열 비교 실수가 애초에 끼어들 자리가 적다.

**"그럼 어차피 SQL도 실수하는데, 고치기 쉬운 A가 낫지 않냐"는 반론도 나왔었다.** 처음엔 "B(SQL)는 고치는 비용이 크다"고 주장했는데, 다시 보니 과장이었다 — 이 프로젝트는 ADR-007로 이미 "PR 올리면 CI가 마이그레이션 자동 push"까지 자동화돼 있어서, SQL을 고치는 것도 파이썬을 고치는 것과 똑같이 PR+CI 사이클을 탄다. 즉 "고치는 비용" 자체는 A/B가 별 차이가 없다는 게 정정된 결론이었다. 그래서 "고치기 쉬움"이 아니라, "애초에 얼마나 자주 틀리느냐"와 "이 리포트 로직이 앞으로 얼마나 복잡해질 예정이냐" 두 가지가 진짜 결정 기준이 됐다.

지금 리포트 요구사항(합계 + 비교%)은 단순해서 SQL이 맡아도 충분히 안전하지만, 앞으로 "동기부여 문구 생성", "인사이트 추가" 같은 요구가 올 걸 감안하면 그 부분만큼은 파이썬에 남겨두는 게 ADR-002(집계·추천 로직은 파이썬이 편하다)의 취지와도 맞다. 그래서 "버그 여지가 있는 단순 합계는 SQL에, 앞으로 자주 바뀔 해석·표현 로직은 파이썬에" 나누는 C가 지금까지 나온 논의를 전부 반영한 절충안이었다.

## 포기한 것

- 로직을 한 언어로 통일하는 걸 포기한다. B였다면 전부 SQL, A였다면 전부 Python으로 깔끔하게 정리됐을 텐데, C는 SQL과 Python 두 군데에 로직이 나뉜다. ADR-002가 이미 "시스템이 둘로 나뉜다 — 로직이 어디 있는지 헷갈릴 수 있다"고 경고한 비용을 그대로 받아들인 것이다.
- 완전한 최적화(SQL이 다 함)를 포기한다. 지금 규모에선 차이가 없지만, 나중에 유저가 아주 많아지면 A/C 방식(파이썬 쪽 로직)이 SQL 전용(B안)보다 서버 부하가 더 클 수 있다.

## 당시 몰랐던 것

- 주간 리포트에 구매 내역(coin_ledger)까지 넣을지 범위가 아직 확정 안 됐다.
- JWT 인증(ADR-010)이 아직 구현 전이라, 인증된 user_id를 SQL 함수에 어떻게 넘길지(RPC 파라미터로 명시 전달 vs auth.uid() 암묵 사용)도 미정이다.
- SQL 함수를 RPC로 노출할지, FastAPI가 직접 쿼리할지도 안 정함 — 다른 RPC들(buy_item, complete_mission)처럼 security definer RPC로 만들지, 아니면 FastAPI가 SELECT만 날릴지는 구현 시 결정.
