## 1. 전역 인증 필터가 생겼다 — `common/auth/SecurityConfig.java`

8/11에 "이 리졸버가 인증 검사 전부라 컨트롤러가 `@CurrentUserId`를 깜빡하면 그 엔드포인트는 그냥 열린다"고 적어뒀던 리스크가 **해결됐다.**

```java
private static final String[] PUBLIC_PATHS = {
        "/auth/**", "/actuator/health", "/health", "/error"
};

http
    .cors(cors -> cors.configurationSource(corsConfigurationSource()))
    .csrf(csrf -> csrf.disable())
    .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .exceptionHandling(ex -> ex.authenticationEntryPoint(unauthorizedEntryPoint()))
    .authorizeHttpRequests(auth -> auth
            .requestMatchers(PUBLIC_PATHS).permitAll()
            .anyRequest().authenticated()          // ← 나머지 전부 인증 필수
    )
    .addFilterBefore(jwtAuthenticationFilter(), UsernamePasswordAuthenticationFilter.class);
```

**개념: 화이트리스트 = 기본 거부(deny by default).** 예전 구조는 "리졸버를 붙인 곳만 보호"였으니 실수하면 **열리는** 방향이었다. 지금은 "명시한 곳만 열고 나머지는 다 막음"이라 실수해도 **닫히는** 방향이다. 새 컨트롤러를 추가해도 자동으로 보호된다.

나머지 설정도 각각 이유가 있다.

- `STATELESS` — 서버가 세션을 안 만든다. 매 요청이 토큰만으로 자기 증명을 해야 하니 서버를 여러 대로 늘려도 세션 공유 문제가 없다.
- `csrf.disable()` — CSRF 공격은 브라우저가 쿠키를 자동으로 실어 보내는 것을 악용한다. 이 서비스는 쿠키가 아니라 `Authorization` 헤더를 쓰므로 자동 전송 자체가 없다. 그래서 끈다.
- CORS는 Firebase Hosting 주소 2개만 허용 + `setAllowCredentials(false)` — 쿠키를 안 쓰니 credentialed 요청을 허용할 이유가 없다.

```java
if (header != null && header.startsWith("Bearer ")) {
    try {
        var userId = jwtService.getUserId(token);
        var auth = new UsernamePasswordAuthenticationToken(userId, null, List.of());
        SecurityContextHolder.getContext().setAuthentication(auth);
    } catch (Exception ignored) {
        // 유효하지 않은 토큰 — SecurityContext 비움 → 401
    }
}
filterChain.doFilter(request, response);
```

필터가 직접 401을 던지지 않고 **SecurityContext를 비워둔 채 통과**시키는 게 포인트다. 거부 판단은 뒤에 있는 Spring Security가 하고, 필터는 "신원 확인"만 한다. 책임이 한 군데씩만 있다.

## 2. 토큰을 두 종류로 구분하는 법 — `auth/JwtService.java`

```java
private static final String CLAIM_TYPE = "typ";
private static final String TYPE_ACCESS = "access";
private static final String TYPE_REFRESH = "refresh";

public UUID getUserId(String token) {
    try {
        var claims = Jwts.parser().verifyWith(key).build()
                .parseSignedClaims(token).getPayload();
        if (!TYPE_ACCESS.equals(claims.get(CLAIM_TYPE, String.class))) {
            throw new ApiException(HttpStatus.UNAUTHORIZED, "INVALID_TOKEN", "유효하지 않은 토큰입니다.");
        }
        return UUID.fromString(claims.getSubject());
    } catch (JwtException | IllegalArgumentException e) {
        throw new ApiException(HttpStatus.UNAUTHORIZED, "INVALID_TOKEN", "유효하지 않은 토큰입니다.");
    }
}
```

**왜 `typ` 클레임을 확인하나** — access와 refresh는 같은 키로 서명되므로 서명 검증만으로는 구분이 안 된다. 확인을 안 하면 수명이 긴 refresh 토큰으로 일반 API를 계속 호출할 수 있다. 짧은 수명으로 피해를 줄이려던 설계가 무력화되는 것.

> **refresh 토큰에만 `jti`(랜덤 UUID)를 넣는 이유** — 주석에 답이 있다. JWT의 `iat`/`exp`는 NumericDate라 초 단위다. 같은 초에 같은 사용자에게 두 번 발급하면 `sub`/`typ`/`iat`/`exp`가 전부 같아져 토큰 문자열이 동일해진다. `refresh_token.token_hash`에 UNIQUE가 걸려 있어 충돌하고, 토큰 회전(rotation)도 깨진다. 매 발급마다 랜덤 `jti`를 넣어 항상 다른 문자열이 되게 만든다.

## 3. 비밀번호 해시가 Argon2id로 바뀌었다 — `auth/PasswordEncoderConfig.java`

```java
// TRD §3 스택 표 — 비밀번호 해시는 Argon2id로 확정(user_credential.password_algo CHECK
// 제약이 'argon2id' 고정값만 허용한다). 기존 BCryptPasswordEncoder에서 교체.
@Bean
public PasswordEncoder passwordEncoder() {
    return Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8();
}
```

- **BCrypt vs Argon2id** — 둘 다 "느리게 만들어서" 무차별 대입을 막는 단방향 해시다. 차이는 Argon2id가 **메모리를 많이 쓰도록(memory-hard)** 설계됐다는 점. GPU는 코어가 많아 연산 병렬화에는 강하지만 코어당 메모리는 적어서, 메모리를 요구하면 대량 병렬 공격의 비용이 확 올라간다.
- 런타임 구현체가 필요해서 `build.gradle`에 `bcprov-jdk18on`(BouncyCastle)이 `runtimeOnly`로 들어가 있다.
- 배울 점: **DB의 CHECK 제약(`password_algo = 'argon2id'`)과 코드가 한 몸으로 움직인다.** 코드만 바꾸면 DB가 거부하고, DB만 바꾸면 코드가 다른 값을 넣는다. 스펙 문서(TRD)가 양쪽을 동시에 강제하는 구조.

## 4. 엔티티에 `title` 컬럼이 아예 없다 — `event/Event.java`

```java
// ERD v3.1 `event`. 외부 캘린더 제목 원문은 저장하지 않는다(절대 원칙 8) — title 컬럼 자체가 없다.
// 표시명은 사용자가 입력·승인한 displayLabel만 (TRD D17).
@Entity
@Table(name = "event")
public class Event {

    @Id @GeneratedValue(strategy = GenerationType.UUID)
    private UUID eventId;

    @Version
    @Column(nullable = false)
    private Long revision;
    // ...
    @Setter
    private String displayLabel; // 사용자가 입력·승인한 값만. 외부 제목 원문은 절대 여기 들어가지 않는다
}
```

**개념 ① `@Version` = 낙관적 락(optimistic locking).** 행을 잠그지 않고, 수정할 때마다 `revision`이 1씩 올라간다. 내가 읽은 시점의 revision과 저장 시점의 revision이 다르면 "그 사이 누가 바꿨다"는 뜻. 뒤에 나올 AI 분류에서 이 값을 그대로 활용한다.

**개념 ② 프라이버시가 스키마를 결정한다.** 구글 캘린더 제목을 안 쓰는 게 아니라 저장할 자리를 아예 없앴다. 실수로 저장하는 코드를 짜는 것 자체가 컴파일되지 않는다. "저장하지 않으면 유출될 것도 없다"를 주석이 아니라 구조로 강제한 사례.

`@Setter`가 필드별로 붙어 있는 것도 그대로다 — `eventId`, `userId`, `createdAt`, `revision`엔 setter가 없어 생성 후 못 바꾼다.

## 5. 락을 이름으로 드러내는 리포지토리 — `event/EventRepository.java`

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select e from Event e where e.eventId = :eventId and e.userId = :userId")
Optional<Event> findOwnedForUpdate(UUID eventId, UUID userId);

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select e from Event e where e.eventId = :eventId")
Optional<Event> findByIdForUpdate(UUID eventId);
```

**개념: 비관적 락(pessimistic lock).** `PESSIMISTIC_WRITE`는 SQL의 `SELECT ... FOR UPDATE`로 번역된다. 트랜잭션이 끝날 때까지 그 행을 다른 트랜잭션이 못 건드린다.

| | 낙관적 락 (`@Version`) | 비관적 락 (`FOR UPDATE`) |
|---|---|---|
| 방식 | 일단 진행하고 저장할 때 충돌 확인 | 읽는 순간 행을 잠그고 시작 |
| 유리한 상황 | 충돌이 드물 때 | 충돌이 잦거나 반드시 막아야 할 때 |
| 이 프로젝트의 쓰임 | AI 결과가 낡았는지 판정 | 사용자 수정과 동기화가 겹칠 때 직렬화 |

메서드 이름에 `ForUpdate`를 박아둔 게 좋다 — 호출부에서 "여기는 락이 걸린다"가 바로 보인다.

> **팀 규칙: 락 순서는 항상 Event → review** (`tasks/lessons.md`, `tasks/todo.md`의 Constraints)
> 여러 트랜잭션이 서로 다른 순서로 여러 행을 잠그면 데드락이 난다. A가 Event→review 순으로, B가 review→Event 순으로 잠그면 서로를 영원히 기다린다. 순서를 하나로 고정하는 게 데드락 예방의 정석이고, 이 팀은 그걸 문서에 못박고 모든 writer가 따르게 했다.
> 실제로 겪은 사고도 기록돼 있다 — "Event를 건드릴 수 있는 모든 writer는 Event-first 락 순서에 참여해야 한다. 행 락 없는 트랜잭션 writer는 낡은 엔티티 스냅샷을 사용자 소유 필드 위에 덮어쓸 수 있다."

## 6. 같은 요청을 두 번 보내도 한 번만 — `idempotency/`

네트워크가 끊겨 클라이언트가 재시도하면 결제가 두 번 되는 식의 사고를 막는 장치. **Idempotency-Key 패턴**이라고 부른다.

```java
String idempotencyKey = request.getHeader("Idempotency-Key");
if (idempotencyKey == null || idempotencyKey.isBlank() || !"POST".equalsIgnoreCase(request.getMethod())) {
    filterChain.doFilter(request, response);   // 헤더 없으면 평소대로
    return;
}

// 같은 (user, key, endpoint) 기록이 있으면 저장해둔 응답을 그대로 재생
Optional<IdempotencyRecord> existing = idempotencyService.find(userId.get(), idempotencyKey, endpoint);
if (existing.isPresent()) {
    response.setStatus(record.getStatusCode());
    response.getWriter().write(record.getResponseBody());
    return;
}

ContentCachingResponseWrapper wrapped = new ContentCachingResponseWrapper(response);
filterChain.doFilter(request, wrapped);

// 2xx만 저장
if (wrapped.getStatus() >= 200 && wrapped.getStatus() < 300) {
    idempotencyService.store(userId.get(), idempotencyKey, endpoint, wrapped.getStatus(), body);
}
wrapped.copyBodyToResponse();   // 캐싱 래퍼는 이걸 안 하면 실제 응답이 안 나간다
```

설계 판단 세 개가 전부 배울 만하다.

1. **2xx만 저장** — 실패 응답까지 캐시하면 재시도해도 영원히 같은 실패가 재생된다. 일시적 오류는 재시도로 풀려야 한다.
2. **헤더가 없으면 그냥 통과** — 이미 머지된 엔드포인트를 건드리지 않고, 프론트가 헤더를 보내기 시작하는 곳부터 자연스럽게 적용된다. 소급 적용을 안 하는 점진적 도입 전략.
3. **동시 요청의 unique 위반은 무시** (`IdempotencyService.store`) — 같은 키로 두 요청이 동시에 들어와 제약을 위반하면, 이미 다른 쪽이 저장했다는 뜻이므로 조용히 넘어간다. 원래 응답은 이미 나간 뒤라 문제없다.

> **코드가 스스로 밝힌 한계** — 필터는 서블릿 레벨이라 컨트롤러가 이미 커밋한 다음에 응답을 가로챈다. 즉 저장이 컨트롤러의 `@Transactional`과 같은 트랜잭션이 아니다. 그 사이 아주 좁은 창에서 크래시가 나면 원본 작업은 성공했는데 멱등성 기록은 없는 상태가 되어 재시도 시 중복 실행될 수 있다.
> 완벽한 원자성이 필요해지면 서비스 트랜잭션 안에서 직접 기록하도록 승격한다고 주석에 적혀 있다. 한계를 숨기지 않고 조건과 함께 남겨두는 것이 이 코드베이스의 일관된 습관이다.

## 7. 외부 호출은 트랜잭션 밖으로 — `common/transaction/TransactionConfig.java`

```java
// 외부 API 호출(구글 토큰 검증 등)을 트랜잭션 밖에서 하고, DB 쓰기만 짧게 감싸고 싶을 때 쓴다
// (FCM 전송을 트랜잭션 밖에 두는 것과 같은 원칙). @Transactional로 메서드 전체를 감싸면
// 클래스 내부 호출(self-invocation)엔 프록시가 안 걸려서 TransactionTemplate으로 대신한다.
@Bean
public TransactionTemplate transactionTemplate(PlatformTransactionManager transactionManager) {
    return new TransactionTemplate(transactionManager);
}
```

**개념 ① 왜 외부 호출을 트랜잭션 밖으로 빼나** — 트랜잭션이 열려 있는 동안은 DB 커넥션을 붙잡고 있다. 그 안에서 응답이 10초 걸리는 외부 API를 호출하면 커넥션을 10초 동안 점유한다. 이런 요청이 몇 개만 겹쳐도 커넥션 풀이 고갈되어 서비스 전체가 멈춘다.

**개념 ② self-invocation 함정** — `@Transactional`은 스프링이 만든 프록시가 가로채서 동작한다. 같은 클래스 안에서 `this.someMethod()`로 부르면 프록시를 거치지 않아 트랜잭션이 안 걸린다. 그럴 때 `TransactionTemplate`으로 "여기서부터 여기까지"를 코드로 직접 감싼다.

## 8. AI 연동은 왜 이렇게 잘게 쪼개졌나 — `event/classification/`

이 패키지가 지금 백엔드에서 제일 정교한 부분이다. 하는 일은 한 줄로 요약된다 — **외부 캘린더에 새 일정이 들어오면 제목만 OpenAI에 보내 온라인/오프라인 일정인지 분류하고, 그 결과를 "사용자 확인용 질문"으로만 저장한다.**

```java
public ClassificationAttemptOutcome classifyCreated(
        UUID userId, UUID eventId, Long eventRevision, String rawTitle, int remainingProviderCalls) {
    if (remainingProviderCalls <= 0) {                    // ① 호출 예산
        metrics.recordCall(AiCallOutcome.SKIPPED_BUDGET);
        return ClassificationAttemptOutcome.SKIPPED_BUDGET;
    }
    AiGateOutcome gateOutcome = gate.evaluate(userId);    // ② 동의·롤아웃·설정 게이트
    if (gateOutcome != AiGateOutcome.ALLOWED) {
        return skippedGateOutcome(gateOutcome);
    }
    Optional<String> normalizedTitle = titleNormalizer.normalize(rawTitle);  // ③ 입력 정규화
    if (normalizedTitle.isEmpty() || eventId == null) {
        return ClassificationAttemptOutcome.SKIPPED_INVALID_INPUT;
    }
    if (!concurrencyGuard.tryAcquire()) {                 // ④ 전역 동시 호출 제한
        metrics.recordCall(AiCallOutcome.SKIPPED_BUSY);
        return ClassificationAttemptOutcome.SKIPPED_BUSY;
    }
    try {
        Optional<EventClassificationResult> result = classifier.classify(...);  // ⑤ 외부 호출
        if (result.isEmpty()) return ClassificationAttemptOutcome.PROVIDER_EMPTY;
        return switch (reviewWriter.createIfEligible(eventId, eventRevision, result.get(), Instant.now())) { // ⑥ 저장
            case CREATED -> ClassificationAttemptOutcome.REVIEW_CREATED;
            case DUPLICATE -> ClassificationAttemptOutcome.REVIEW_DUPLICATE;
            case STALE -> ClassificationAttemptOutcome.REVIEW_STALE;
        };
    } catch (RuntimeException ignored) {
        // 분류/저장 실패가 캘린더 sync-token 전진을 막으면 안 된다
        return ClassificationAttemptOutcome.PROVIDER_EMPTY;
    } finally {
        concurrencyGuard.release();
    }
}
```

**핵심은 모든 분기가 예외가 아니라 "정상적인 스킵"으로 수렴한다는 것이다.** 예산 초과, 동의 없음, 롤아웃 제외, 동시 호출 과다, 응답 없음, 낡은 결과 — 전부 이름 붙은 결과값(enum)으로 돌아온다. 이걸 **fail-closed**라고 한다. 어긋나면 아무것도 하지 않는다가 기본값.

### 게이트 — 전부 만족해야 통과 (`AiClassificationGate`)

```java
static int rolloutBucket(UUID userId) {
    byte[] digest = MessageDigest.getInstance("SHA-256")
            .digest(userId.toString().getBytes(StandardCharsets.UTF_8));
    // ... 앞 8바이트를 long으로 → 100으로 나눈 나머지
    return (int) Long.remainderUnsigned(firstEightBytes, 100);
}
```

- **안정 해시 롤아웃** — 유저 ID를 해시해 0~99 버킷에 넣고, `rolloutPercent`보다 작은 버킷만 대상이 된다. 랜덤이 아니라 해시라서 같은 유저는 언제 호출해도 같은 버킷이다. 5% → 25% → 100%로 올려도 기존 대상은 계속 대상으로 남는다.
- **동의는 정확 일치로만** — 최신 privacy 동의가 `agreed`이고 정책 버전 문자열까지 정확히 같아야 통과한다. 버전이 올라가면 자동으로 다시 막힌다.
- API 키·핀 고정된 모델명·승인된 HTTPS 엔드포인트·타임아웃까지 전부 유효해야 `enabled`로 친다. 설정이 하나라도 비면 조용히 no-op.

### 저장 — 락 + revision 재검증 (`EventClassificationReviewWriter`)

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public CreateReviewOutcome createIfEligible(
        UUID eventId, Long expectedEventRevision, EventClassificationResult result, Instant askedAt) {
    Event event = eventRepository.findByIdForUpdate(eventId).orElse(null);   // 행 잠그고
    if (!isEligible(event) || !expectedEventRevision.equals(event.getRevision())) {
        return CreateReviewOutcome.STALE;                                     // 그 사이 바뀌었으면 폐기
    }
    int inserted = reviewRepository.insertPendingIfAbsent(...);               // DB 제약으로 중복 차단
    return inserted == 1 ? CreateReviewOutcome.CREATED : CreateReviewOutcome.DUPLICATE;
}
```

여기 한 메서드에 오늘 나온 개념이 다 모여 있다.

- `REQUIRES_NEW` — 호출한 쪽 트랜잭션과 분리된 새 트랜잭션. review 저장이 실패해도 이미 저장된 Event를 롤백시키지 않는다.
- `findByIdForUpdate` — 비관적 락으로 사용자 수정과 겹치지 않게 직렬화.
- `expectedEventRevision.equals(...)` — 낙관적 revision으로 stale 판정. AI 응답이 오는 동안 사용자가 일정을 수정했다면 그 분류 결과는 낡은 것이므로 버린다. (시각(timestamp) 대신 revision을 쓰는 이유는 팀 문서에 있다 — "타임스탬프는 JVM과 PostgreSQL의 정밀도 경계를 넘나드는 안전한 stale 판정 토큰이 아니다.")
- `insertPendingIfAbsent` — 애플리케이션 선검사만 믿지 않고 DB의 partial unique index로 한 번 더 막는다. 검사와 삽입 사이의 틈(TOCTOU)은 결국 DB만 닫을 수 있다.
